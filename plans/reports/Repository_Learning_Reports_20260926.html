3. 상태 전이로 이해할 운영 원리

3.1 시작·트래픽 수신·재시작을 분리한다

3.2 SSE와 장시간 작업은 Pod 수명보다 길 수 있다

Pod 종료 시 종료 신호와 grace period가 주어지고, 시간이 만료되면 남은 프로세스가 강제 종료될 수 있다. 종료 중 endpoint의 ready 상태는 false가 되지만 이미 열린 연결 처리까지 애플리케이션 대신 완성해 주지는 않는다.[K03]

설계 제안: 새 요청 차단 → 새 queue 작업 인수 중단 → 진행 작업·cursor 저장 → 가능한 연결 종료·결과 게시 → 소유권 반납 순서를 기존 worker 계약에 맞춘다. 종료 중 저장이 실패하면 lease 만료 후 재인수하되, 새 worker만 결과를 확정하도록 fence/attempt를 검사한다. 요청 ID, 작업 ID, 실행 attempt, 외부 provider request ID를 구분한다.

SSE 재접속은 전송 복구이고 동일 생성 작업 재실행은 업무 재시도다. 클라이언트 재연결 때마다 유료 모델 호출을 새로 만들면 중복 결과·중복 과금이 생긴다. 이미 실행 중인 작업 조회·이벤트 재생 기능이 없다면 먼저 그 계약을 설계한다. terminationGracePeriodSeconds만 크게 늘려 해결했다고 판단하지 않는다. proxy idle timeout과 buffering, 앱 heartbeat, 최대 작업시간도 함께 확인해야 한다.

3.3 Job·CronJob은 정확히 한 번 실행을 보장하지 않는다

Job은 parallelism=1, completions=1이어도 같은 프로그램이 두 번 시작될 수 있다. CronJob도 특정 시각의 Job 생성이 중복되거나 누락될 수 있어 멱등성이 필요하다. concurrencyPolicy: Forbid는 해당 CronJob이 생성한 Job 사이의 겹침 제어이며, 다른 CronJob·수동 실행·앱 자체 재시도 전체의 중복을 해결하지 않는다.[K06][K07]

설계 제안: 업무상 동일 작업을 뜻하는 key로 중복을 판단한다. 예를 들어 입력 artifact hash + 작업 종류 + 알고리즘 버전을 사용하고, 고유 제약과 결과 확정을 동일 트랜잭션 또는 검증된 outbox 방식으로 묶는다. 작업 완료 기록 전에 process가 죽는 경우와 외부 API가 처리한 뒤 응답만 잃는 경우를 별도 실험한다. 외부 서비스가 idempotency key를 지원하지 않으면 정확히 한 번 처리라고 약속하지 않는다.

3.4 저장 용량·영속성·가용성·복구 가능성은 다르다

local PV는 특정 노드의 장치·경로에 연결된다. 그 노드가 불능이면 다른 노드에 Pod를 만들더라도 해당 데이터를 사용할 수 없다. 노드 제약은 PV의 nodeAffinity로 표현하며, WaitForFirstConsumer는 PVC 바인딩과 Pod 배치 조건을 함께 결정하는 데 쓰인다.[K04]

과거의 13TB ext4 기록만으로는 local PV인지, K3s local-path provisioner의 hostPath 계열인지, 분산 저장소인지 판별할 수 없다. 실제 PV의 spec.local, spec.hostPath, spec.csi, StorageClass provisioner와 nodeAffinity를 읽어 구분한다. 13TB라는 용량은 HA나 백업의 증거가 아니다. 같은 Proxmox 호스트 안 VM 여러 개도 호스트·전원·디스크 장애를 함께 겪을 수 있다.

복구 설계 제안: ① Git/이미지/설정, ② 애플리케이션 DB와 업로드 파일, ③ k3s control-plane datastore를 각각 복구 대상으로 관리한다. k3s datastore 백업 방식은 SQLite·외부 DB·embedded etcd에 따라 다르며 server token도 복구에 필요하다.[K14] 이 token은 보관 절차에만 포함하고 보고서·로그·Git에 기록하지 않는다. 애플리케이션 데이터 복구는 별도 절차이며, 백업 파일 존재만으로 끝내지 않고 격리 환경에서 복원 후 핵심 조회를 검증한다.

3.5 HPA는 외부 모델 사용량·DB 용량을 늘리지 않는다

CPU utilization 방식 HPA는 CPU request를 기준으로 계산하며 metrics API가 필요하다. queue 길이·대기시간을 사용하려면 이를 공급하는 custom/external metrics 구성이 있어야 한다. ResourceQuota는 namespace의 허용 자원을 제한하며 위반하는 Pod 생성이 거부될 수 있다.[K08][K09]

설계 제안: AI API 호출 서버가 외부 RPM/TPM·계정별 동시성에 막힌다면 replica 증가는 유효 처리량을 늘리지 못한다. 우선 global admission limit을 기존 router/queue와 공유한다. worker별 동시성 × 최대 replica가 전체 한도를 넘는지 검사한다. DB connection pool도 replica 수에 비례해 합산한다. 지표는 CPU 하나보다 대기시간·활성 작업·429·실패율·메모리 최고치를 함께 보고, scale-down 시 실행 중 작업의 처리를 정한다.

3.6 RBAC와 NetworkPolicy는 서로 다른 경계를 제어한다

RBAC는 Kubernetes API 동작 권한을 제한한다. 서비스 계정 권한은 필요한 namespace와 verb로 좁히고, API가 필요 없는 서버는 token 자동 마운트를 끄는 방식을 검토한다. NetworkPolicy는 네트워크 통신을 제어하지만 이를 구현하는 네트워크 구성요소가 없으면 리소스를 생성해도 차단되지 않는다.[K10][K11]

K3s에는 기본 NetworkPolicy controller가 포함되지만 실행 옵션으로 비활성화할 수 있다. 따라서 “Flannel이므로 정책 없음”도, “YAML을 만들었으므로 격리됨”도 실제 확인 없이 단정하지 않는다. K3s 기본 Traefik 설정은 관리되는 파일을 직접 고치는 대신 해당 버전에 맞는 HelmChartConfig를 사용하도록 문서화되어 있다.[K12]

검증 제안: 정책이 허용해야 하는 DNS·DB·queue·provider 통신과 거부해야 하는 다른 namespace 통신을 각각 실험한다. IP 허용만으로 외부 서비스의 사용자 인증이 대체되지 않는다.

3.7 Forgejo SSH: nodePort·port·targetPort를 구분한다

Service의 port는 Service가 받는 포트, targetPort는 Pod로 전달할 포트, nodePort는 NodePort Service의 노드 측 외부 포트다. 이름 기반 targetPort도 가능하다.[K13]

과거 기록의 30222 → 22 → 2222는 가능한 매핑 예시이며 현재 설정값이 아니다. 실제 Service, EndpointSlice, Pod 설정과 SSH 서버 리스닝 포트를 비교한 뒤 판단한다. containerPort: 2222 선언만으로 서버가 2222를 listen하지는 않는다. 일반 HTTP Ingress가 SSH TCP 전달을 자동 구성하는 것도 아니다. 클라이언트에 표시하는 clone URL 포트와 실제 노출 포트가 일치해야 하므로 Forgejo 앱 설정과 네트워크 설정 양쪽을 확인한다. 숫자만 보고 무조건 2222로 patch하지 않는다.

3.8 mirror는 배포 원본 자동 판정 수단이 아니다

설계 제안: 프로젝트마다 canonical repo·배포 branch·검증 SHA·이미지 digest·chart 버전을 한 묶음으로 기록한다. Forgejo와 GitHub mirror 양쪽에 동일 애플리케이션을 갱신하는 독립 reconciler를 연결하면 운영 소유권이 충돌할 수 있다. 같은 이름·비슷한 최근 시각은 내용 동일성의 증거가 아니므로 SHA/tree와 동기화 상태를 확인한다.

Flux 도입 시 GitRepository는 branch나 commit으로 추적 대상을 지정할 수 있고 관측한 revision을 상태로 노출한다.[K17] 현재 Flux/Argo CD 설치를 확인한 것은 아니며 새 도구 도입을 전제로 하지 않는다. 현재 CI/배포 흐름이 충분하면 먼저 그 흐름에서 단일 원본과 SHA 추적을 정리한다. 대용량 binary가 추적된 저장소는 배포 context와 source artifact를 분리해야 하며, 근거 없는 이력 삭제나 force push는 하지 않는다.

4. 운영 변경 없이 수행할 수 있는 진단 절차

아래는 작성된 명령이며 미실행이다. 실제 context·namespace·resource명을 확인한 운영자가 적용할 수 있도록 변수로 구분했다. kubeconfig 원문, Secret, 토큰을 출력하는 명령은 포함하지 않는다. 로그·describe 결과에도 업무 데이터가 있을 수 있으므로 공유용 기록에는 필요한 필드만 남긴다.

# 1) 대상과 버전 확인: 아래 세 변수는 실제 조회한 값으로 채운다.
kubectl config current-context
kubectl version -o yaml
helm version --short
K8S_CTX='확인한-context'
K8S_NS='확인한-namespace'
K8S_WORKLOAD='확인한-deployment-name'

# 2) 상태 → 사건 → 이전 종료 원인 순서로 읽는다.
kubectl --context "$K8S_CTX" get nodes -o wide
kubectl --context "$K8S_CTX" -n "$K8S_NS" get deploy,sts,pods,svc,ingress,pvc,hpa
kubectl --context "$K8S_CTX" -n "$K8S_NS" get events --sort-by=.metadata.creationTimestamp
kubectl --context "$K8S_CTX" -n "$K8S_NS" describe deployment "$K8S_WORKLOAD"
kubectl --context "$K8S_CTX" -n "$K8S_NS" rollout status deployment/"$K8S_WORKLOAD" --timeout=30s

# 3) 오류 Pod를 특정한 뒤 현재/이전 container 로그를 분리한다.
K8S_POD='확인한-pod-name'
K8S_CONTAINER='확인한-container-name'
kubectl --context "$K8S_CTX" -n "$K8S_NS" describe pod "$K8S_POD"
kubectl --context "$K8S_CTX" -n "$K8S_NS" logs "$K8S_POD" -c "$K8S_CONTAINER" --timestamps --tail=150
kubectl --context "$K8S_CTX" -n "$K8S_NS" logs "$K8S_POD" -c "$K8S_CONTAINER" --previous --timestamps --tail=150

# 4) 연결 실패: Service 선택과 EndpointSlice를 먼저 확인한다.
K8S_SERVICE='확인한-service-name'
kubectl --context "$K8S_CTX" -n "$K8S_NS" get service "$K8S_SERVICE" -o yaml
kubectl --context "$K8S_CTX" -n "$K8S_NS" get endpointslices -l "kubernetes.io/service-name=$K8S_SERVICE" -o yaml
kubectl --context "$K8S_CTX" -n "$K8S_NS" get networkpolicy

# 5) 저장·할당·기존 릴리스 상태. top은 metrics API가 없으면 실패할 수 있다.
kubectl --context "$K8S_CTX" get storageclass,pv
kubectl --context "$K8S_CTX" -n "$K8S_NS" get resourcequota,limitrange
kubectl --context "$K8S_CTX" -n "$K8S_NS" top pods
helm --kube-context "$K8S_CTX" -n "$K8S_NS" list

--previous에 이전 container가 없거나 top에 metrics API가 없으면 그 결과 자체가 관측 내용이다. 조회 실패를 애플리케이션 장애로 단정하지 않는다. delete pod, rollout restart, drain, scale, patch, helm upgrade는 진단 조회와 다른 변경 작업이다.[K18]

6. 배포·rollback 통과 조건

단계 반드시 남길 증거 실패 시 판단
원본 고정 canonical repo, base/head SHA, 미병합 변경, 이미지 digest, chart/values 버전 mirror 최신성이나 PR 병합 상태가 불명확하면 멈춤
저장소 검증 기존 테스트·빌드·lint 및 실제 실행 entrypoint, NO-GO/guard 상태 문서상 구현 완료나 prototype 동작으로 대체 불가
정적 배포 검증 현 chart의 lint/template, API 호환, ports/probes/resources, secret 참조 빈 helm 저장소를 운영 chart 보유로 취급하지 않음
복구 준비 데이터 backup 식별자, 복원 시험 결과, 이전 image/values, schema 호환성 되돌릴 수 없는 migration이면 별도 전환 계획 선행
제한된 검증 격리 환경에서 auth·파일·SSE·작업 재실행·종료 처리 기능별 실패 위치를 남기고 원인 수정 후 재검증
운영 전환 후 확인 Ready와 핵심 flow, 5xx·429·대기시간·중복·자원 사용 사전 합의한 기준 초과 시 rollback 또는 forward fix

Helm 3 공식 upgrade 문서는 --atomic을, 현행 Helm 문서는 --rollback-on-failure를 설명한다. 과거 설치 기록만으로 현재 major를 정하지 말고 helm version과 해당 버전의 helm upgrade --help를 확인한다.[K15][K16] Helm release rollback은 이전 Kubernetes 리소스 구성으로의 복귀 절차이며, 외부 API 부작용·DB migration·삭제된 데이터까지 원복했다는 증거가 아니다. rollback 후에도 별도 데이터·업무 검증이 필요하다.[K19]

7. 현재 저장소를 사용하는 4주 학습 계획

달력상 진도보다 근거 기반 통과 조건을 우선한다. 한 주의 조건이 미충족이면 실제 운영 배포를 생략하고 격리 실험과 문서·코드 분석을 계속한다. 아래는 실행 예약이 아니라 학습 계획이다.

주차 저장소 연결 학습 질문·실습 제출할 산출물 완료 판정
1주: 원본과 실행 경계 Forgejo/GitHub mirror 전체, 빈 helm, FilamAI meta·child 같은 이름이 같은 소스인가? submodule/gitlink와 child SHA가 무엇을 보장하는가? NO-GO guard가 어떤 실행을 차단하는가? repo→SHA→entrypoint→상태 저장소→외부 의존성 표. 서버/클라이언트/자료/backup 분류 최소 한 서버 후보의 실제 build/run 경로를 설명하고 차단 이유를 증거 파일로 연결
2주: 요청과 종료 AI-server gateway 후보, WLatch main과 미병합 PR #14 Ready와 Running이 왜 다른가? 요청 중 프로세스가 종료되면 어떤 상태를 잃는가? worker 중복 인수는 어디서 막히는가? 실제 코드 위치에 연결한 요청·작업 상태 전이, probe/종료 계약 초안, 격리 실험 로그 본문과 미병합 기능을 구분. 하나의 실패를 관측→가설→수정→재검증으로 기록
3주: 데이터와 연결 실행 가능한 backend 후보, Forgejo SSH 운영 기록 PV가 연결된 노드를 잃으면 무엇이 남는가? DB 복제와 백업은 왜 다른가? 30222/22/2222 중 어느 값이 어디에 속하는가? 실제 환경 조회 결과 또는 미검증 목록, 복원 절차, Service/EndpointSlice 매핑 표 복원은 격리 대상으로만 검증. 원본 데이터 훼손 없이 결과 대조; 미접속 시 실습 완료로 표기하지 않음
4주: 확장과 릴리스 검증된 서버 1개, IntelliAlgo의 서버/Flutter 경계, FCN prototype replica를 늘렸을 때 session·queue·DB·provider quota가 어떻게 변하는가? prototype의 성공이 backend 검증을 대신하는가? 한 서버의 제한된 배포 후보, capacity 표, rollback gate, 커밋 기반 추적 표 기능·지표·복구 기준을 통과한 서버만 후보 승격. FCN/FilamAI 선결조건 미해소 시 배포 보류

객관식으로 진행할 때는 먼저 위 상황 중 하나의 다음 상태를 묻고 정답을 숨긴다. 답변 후 실제 코드·공식 규칙·관측값으로 선택지를 검증한다. “명령을 안다”보다 “무슨 증거가 나오면 가설을 바꿀지 설명한다”를 학습 완료 기준으로 삼는다.

전체 저장소 학습·트러블슈팅·Kubernetes 활용 리포트

작성 기준일: 2026-09-26 KST. 원격 조회는 같은 날 순차적으로 수행했다. 저장소별 커밋을 고정해 읽었지만 여러 저장소를 한 시점에 잠그지는 않았으므로, 다른 작업자가 진행 중인 저장소의 변경은 후속 관측으로 별도 기록한다.

핵심 결론은 학습의 기준을 저장소 이름이 아니라 실제 상태 소유권과 완료 조건에 두어야 한다는 것이다. API, 큐, 브라우저 세션, 모바일 클라이언트, 정적 문서, 과거 작업 스냅샷은 서로 다른 운영 단위다. Kubernetes 활용도 각각의 상태·저장소·재시작 조건을 확인한 뒤 결정해야 한다.

조사 범위와 읽는 방법

  • Forgejo 계정 목록 60개와 목록 밖에서 개별 접근을 확인한 nodove/forgejo_mcp 1개, GitHub 연결 목록 13개를 다룬다. 총 74개 저장소 항목이며, 미러·동일 트리·보관본이 포함되어 독립 제품 74개라는 뜻은 아니다.
  • 각 항목에서 학습 주제와 상태 전이, 트러블슈팅 근거와 점검 절차, Kubernetes 적용 판단을 제공한다. 자료만 있는 저장소와 빈 트리도 누락하지 않았다.
  • Forgejo 목록은 /api/v1/user/repos 결과다. 서버 관리자 전역 목록이나 연결되지 않은 GitHub 계정·조직의 모든 저장소를 확보한 것은 아니다. 이번에 확인 가능한 범위의 전수 목록이며, 서버 전체 완전성은 미확인이다.
  • 각 저장소의 기본 브랜치 SHA·트리·대표 소스·구성·문서를 읽었다. 대형 트리의 전체 파일 본문을 전부 읽거나 전체 이력을 감사하지는 않았다. 세부 수집 범위와 제한은 부록 JSON에 남겼다.
  • PR은 보고서에 명시한 페이지와 개수 범위만 읽었다. Forgejo 현재 도구는 issue·review·checks·전체 branch 목록을 노출하지 않는다. 이를 “미해결 이슈 없음”으로 해석하지 않는다.
  • 이 요청은 문서 작성이다. 애플리케이션 소스 수정, PR 병합, 운영 배포 및 장애 주입은 수행하지 않았다. 현재 작업 공간에는 이어서 올릴 기존 Git working tree가 없었다. 다른 IDE·서버의 미업로드 로컬 변경은 접근하지 못했다.

읽는 순서는 주요 프로젝트의 저장소별 리포트 → 공통 Kubernetes 운영 장 → 본인에게 필요한 학습 과제다. 미러 표에서 원본과 동일한 SHA는 같은 소스를 중복 학습할 필요가 없다. SHA가 다르거나 미병합 PR이 있으면 해당 차이를 먼저 확인한다.
