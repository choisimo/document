# LangChain vs LangGraph 제어 흐름 학습 및 기록 노트

> 💡 **이 글을 쓰는 이유:** LangChain과 LangGraph는 둘 다 LLM 애플리케이션을 만들 때 쓰이지만, 문제를 바라보는 모델이 다르다. LangChain은 정해진 순서의 체인에 강하고, LangGraph는 상태를 들고 루프와 분기를 도는 에이전트 흐름에 강하다. 단순 RAG와 복잡한 에이전트를 같은 구조로 밀어붙이지 않기 위해 차이를 기록한다.

---

이 문서는 두 라이브러리의 특정 최신 API를 단정하지 않고, 워크플로를 설계할 때의 선택 기준을 설명합니다. 패키지의 책임과 권장 API는 릴리스마다 바뀔 수 있으므로 실제 결정에는 설치 버전, 공식 마이그레이션 문서, 최소 실행 예제를 함께 기록합니다.

라이브러리를 선택하기 전에 다음 제어 계약을 그립니다.

- 노드별 입력, 출력, 외부 부작용
- 순차 실행, 조건 분기, 반복, 병렬 실행의 필요 여부
- 실행 중 보존할 상태와 각 필드의 갱신 규칙
- 재시도 가능한 오류와 즉시 중단할 오류
- 체크포인트, 중단 후 재개, 사람 승인 경계
- 최대 반복 횟수, 시간·토큰·비용 한도
- 도구 호출의 멱등성과 중복 실행 처리

## 1. 왜 필요한가? (Pain Point & Motivation)

* **이 개념이 구원해 줄 문제:** LLM 워크플로우가 "입력 → 처리 → 출력"으로 끝나는지, 아니면 상태를 보존하면서 반복/분기/승인을 거쳐야 하는지 판단하게 해 준다.
* **대안들의 한계 (기존의 똥떵어리들):** 모든 것을 LangChain 체인으로 만들면 루프와 조건부 라우팅이 복잡해진다. 반대로 단순한 파이프라인에도 LangGraph를 쓰면 상태 머신 설계 비용이 불필요하게 커진다.

## 2. 현재 나의 상태 (Baseline)

* **여기까진 안다 (익숙한 땅):** LangChain은 `Prompt -> LLM -> Output Parser`처럼 정해진 단계가 이어지는 파이프라인에 잘 맞는다.
* **뇌정지 오는 부분 (안개 속):** 에이전트가 실패를 보고 이전 단계로 돌아가거나, 툴 호출 결과에 따라 다음 노드를 바꾸는 순간부터는 단순 체인만으로 제어 흐름이 잘 보이지 않는다.
* **아직은 무리 (워너비):** 상태, 노드, 엣지, 조건부 분기를 명확히 설계해서 실행 경로를 추적할 수 있어야 한다.

## 3. 도달하고 싶은 목표 (Target State)

* **이 글을 끝내고 할 수 있는 일:** 요구사항을 보고 LangChain 체인으로 충분한지, LangGraph 상태 머신이 필요한지 판단한다.
* **이것만은 건지자 (최소 성공 기준):** 짧고 고정적인 흐름은 작은 조합부터 시작하고, 명시적 장기 상태·체크포인트·승인·복구 경계가 필요할 때 그래프 실행 모델을 평가한다. 이를 라이브러리 기능의 절대적인 구분으로 사용하지 않는다.

## 4. 시스템 번역 (Data Flow)

*이 개념을 하나의 살아있는 함수나 파이프라인으로 바라보고 해부해 봅니다.*

* **📥 인풋 (Input):** 사용자 요청, 프롬프트, 검색 결과, 툴 실행 결과, 중간 판단, 사람 승인 여부
* **⚙️ 프로세스 (Processing):** LangChain은 단계별 runnable을 순서대로 실행하고, LangGraph는 공유 상태를 갱신하며 노드와 엣지 조건에 따라 다음 실행 위치를 고른다.
* **📤 아웃풋 (Output):** 최종 답변, 구조화된 결과, 업데이트된 상태, 다음 액션 또는 종료 신호
* **💾 상태 (State):** 이 비교 예시에서는 체인의 단계별 전달값과 그래프의 공유 상태를 구분한다. 상태를 보존하거나 복구하려면 상태 스키마, 필드별 갱신 규칙과 체크포인트 저장 방식을 명시해야 한다.
* **🚨 터지는 조건 (Exception):** 반복이 필요한 문제를 선형 체인에 억지로 넣거나, 단순 작업을 상태 머신으로 과설계할 때 복잡도가 폭발한다.

## 5. 핵심 구성요소 (Building Blocks)

* **레고 블록 1 (LangChain / LCEL):** LLM 호출, 프롬프트, 파서, 검색기 같은 기본 빌딩 블록을 연결하는 체인 중심 프레임워크다.
* **레고 블록 2 (LangGraph State):** 그래프 안의 노드들이 공유하고 갱신하는 실행 메모리다.
* **레고 블록 3 (Nodes & Edges):** 노드는 LLM 호출이나 툴 실행 같은 작업 단위이고, 엣지는 다음 노드로 이동하는 제어 흐름이다.
* **서로 어떻게 맞물려 돌아가는가?:** LangGraph는 LangChain의 컴포넌트를 노드 안에서 활용하면서, 실행 순서는 그래프와 상태 전이 규칙으로 관리한다.

## 6. 상태 전이 (State Transition)

*상태가 어떻게 변하는지 흐름을 한눈에 보여줍니다. (표 안의 문장은 짧고 직관적으로!)*

| 초기 상태 | 이벤트 (트리거) | 전이 조건 | 변경 후 상태 | "바뀐 걸 어떻게 알지?" (관찰 방법) |
| :--- | :--- | :--- | :--- | :--- |
| `REQUESTED` | 사용자 입력 수신 | 고정 파이프라인으로 충분함 | `CHAIN_RUNNING` | LangChain 단계가 순서대로 실행됨 |
| `REQUESTED` | 사용자 입력 수신 | 반복/분기/승인이 필요함 | `GRAPH_RUNNING` | 현재 노드와 공유 상태가 기록됨 |
| `GRAPH_RUNNING` | 툴 실행 완료 | 결과가 충분하지 않음 | `RETRY_OR_ROUTE` | 조건부 엣지가 이전/다른 노드로 이동 |
| `GRAPH_RUNNING` | 품질 기준 충족 | 종료 조건 만족 | `DONE` | 최종 답변과 상태 스냅샷 확인 |

## 7. 불변식 (Invariant: 절대 깨지면 안 되는 규칙)

* **하늘이 무너져도 지켜야 할 조건:** 도구 선택은 실제 제어·복구 계약과 맞아야 한다. 체인도 사용자 코드와 API로 분기·상태를 다룰 수 있고, 그래프도 종료 가드·reducer·부작용 재실행 규칙을 자동으로 보장하지 않는다.
* **이게 깨지면 생기는 대참사:** 체인은 조건문과 예외 처리로 뒤엉키고, 그래프는 불필요한 상태와 노드 때문에 디버깅이 어려워진다.
* **수수방관 금지 (검증법):** 워크플로우를 실행 경로 표로 그려 보고, 루프와 조건부 분기가 실제 요구사항인지 확인한다.

## 8. 가장 작은 예제 (Minimal Viable Example)

* **뇌컴파일이 가능한 수준의 인풋:** "문서를 검색해 답변하라"는 단순 RAG와 "답변 품질이 낮으면 다시 검색하고, 위험한 답변은 사람 승인을 받아라"는 에이전트 요구사항을 비교한다.
* **한 스텝씩 뜯어보기:** 단순 RAG는 `질문 -> 검색 -> 프롬프트 -> LLM -> 파서`로 끝난다. 품질 재검사와 승인 단계가 들어가면 `검색`, `답변`, `검토`, `재검색`, `사람 승인` 노드 사이를 상태에 따라 오가야 한다.
* **해피 엔딩 (결과):** 단순 RAG는 LangChain 체인으로 빠르게 구현하고, 반복 품질 개선 에이전트는 LangGraph 상태 머신으로 투명하게 설계한다.

| 비교 축 | LangChain | LangGraph |
| :--- | :--- | :--- |
| 이 예시의 조합 방식 | Chain / Runnable 조합 | 명시적 상태와 그래프 전이 |
| 검토할 제어 요구 | 짧고 고정적인 경로를 우선 검토 | 반복·분기·중단·재개 경계를 우선 검토 |
| 상태·복구 책임 | 호출자와 구성 요소의 상태·재실행 범위 정의 | 상태 스키마·reducer·체크포인터·재실행 규칙 정의 |
| 주 사용처 | 단순 RAG, 추출, 챗봇 | 자율 에이전트, 멀티 에이전트, Human-in-the-loop |
| 디버깅 관점 | 어느 단계에서 실패했는지 확인 | 어느 상태에서 어떤 엣지를 탔는지 확인 |

## 9. 실패 사례 (What could go wrong?)

* **폭망 시나리오 1:** 반복 수정이 필요한 코드 작성 에이전트를 LangChain 체인 하나로 만들다가 조건문이 여기저기 흩어진다.
* **폭망 시나리오 2:** 단순한 질의응답 파이프라인에 LangGraph를 도입해 노드와 상태 정의만 늘어난다.
* **폭망 시나리오 3:** 공유 상태에 무엇을 저장할지 정하지 않아 노드 간 데이터 계약이 흐려진다.
* **범인 검거 (어떤 불변식이 깨졌나?):** 제어 흐름 복잡도와 도구 선택이 맞아야 한다는 7번 불변식이 깨졌다.

## 10. 뇌 확장하기 (Evolution & Variants)

* **조건을 살짝 바꾸면?:** 반복·승인·장기 상태 때문에 일반 코드의 복구 경계가 불명확해질 때 그래프 실행 모델을 검토한다. 나중에 에이전트로 확장할 가능성만으로 초기 구조를 복잡하게 만들지 않는다.
* **비슷한 놈들과 계급장 떼고 비교하기:** Airflow나 Prefect가 작업 DAG를 관리한다면, LangGraph는 LLM 앱 안의 상태 기반 제어 흐름을 더 세밀하게 다룬다.
* **다른 데서 써먹기:** 챗봇뿐 아니라 문서 생성, 코드 리뷰, 리서치 자동화, 고객 지원 triage 같은 반복 판단형 워크플로우에 적용할 수 있다.

### 실행으로 확인할 조건

같은 최소 워크플로를 두 방식으로 만들 필요는 없습니다. 가장 단순한 후보 하나를 구현하고 다음 조건을 검증합니다.

| 조건 | 확인할 증거 |
| --- | --- |
| 정상 경로 | 노드 순서, 최종 출력, 상태 변화 |
| 모델 오류 | 재시도 횟수와 최종 실패 상태 |
| 도구 시간 초과 | 취소·재개·중복 호출 여부 |
| 사람 승인 | 중단 지점과 승인 전 부작용 차단 |
| 무한 반복 위험 | 반복 상한 도달 시 종료 결과 |
| 프로세스 재시작 | 체크포인트에서의 복구 결과 |
