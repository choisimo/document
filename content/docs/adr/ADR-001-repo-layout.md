# ADR-001: 저장소 레이아웃 재편 학습 및 기록 노트

> 💡 **이 글을 쓰는 이유:** 문서, 인프라 설정, 실행 코드, 빌드 산출물이 한 저장소 안에서 섞이면 파일을 어디에 두고 무엇을 수정해도 되는지 계속 헷갈린다. 이 ADR은 `apps/`, `content/`, `infra/`, `src/`, `dist/`라는 경계를 왜 만들었고, 그 결정이 어떤 문제를 해결하는지 기록한다.

---

## 1. 왜 필요한가? (Pain Point & Motivation)

* **이 개념이 구원해 줄 문제:** MkDocs 콘텐츠, 테마 자산, Docker/Ansible 설정, 자동화 스크립트, 렌더 산출물이 루트와 여러 폴더에 흩어져 있었다. 파일 위치만 보고도 "사람이 읽는 문서인지", "실행되는 코드인지", "배포 설정인지", "빌드 결과인지" 판단할 수 있는 구조가 필요했다.
* **대안들의 한계 (기존의 똥떵어리들):** README만 보강하면 이동 비용은 없지만 탐색 비용과 소유권 문제는 그대로 남는다. 모든 파일을 한 번에 강제 이동하면 CI, 내부 링크, 스크립트 경로가 동시에 깨질 수 있다.

## 2. 현재 나의 상태 (Baseline)

* **여기까진 안다 (익숙한 땅):** 저장소는 MkDocs 기반 문서 허브이고, `content/docs/`가 출판 소스라는 큰 방향은 이미 정해져 있다.
* **뇌정지 오는 부분 (안개 속):** 문서처럼 보이는 파일, 실행 가능한 스크립트, 인프라 설정, 렌더 산출물이 모두 텍스트 파일이라 경계가 흐려지기 쉽다.
* **아직은 무리 (워너비):** 구조 변경 후에도 CI, MkDocs 설정, 내부 링크, 자동화 스크립트가 모두 새 경로를 기준으로 안정적으로 동작해야 한다.

## 3. 도달하고 싶은 목표 (Target State)

* **이 글을 끝내고 할 수 있는 일:** 새 파일을 추가하거나 기존 파일을 옮길 때 어느 최상위 도메인에 속하는지 설명할 수 있다.
* **이것만은 건지자 (최소 성공 기준):** `apps/`, `content/`, `infra/`, `src/`, `dist/`의 책임을 구분하고, `content/docs/`, `content/rendered/`, `content/archive/legacy/`의 편집 규칙을 말할 수 있다.

## 4. 시스템 번역 (Data Flow)

*이 개념을 하나의 살아있는 함수나 파이프라인으로 바라보고 해부해 봅니다.*

* **📥 인풋 (Input):** 새 문서, 렌더 산출물, 배포 설정, 자동화 스크립트, 빌드 결과물
* **⚙️ 프로세스 (Processing):** 파일의 목적을 판정하고 최상위 도메인과 편집 권한 규칙에 맞는 경로로 배치한다.
* **📤 아웃풋 (Output):** 탐색 가능한 저장소 구조, 명확한 소유권, 깨지지 않는 문서 빌드 경로
* **💾 상태 (State):** 현재 파일 위치, MkDocs `docs_dir`, CI 경로, 자동화 스크립트 참조 경로
* **🚨 터지는 조건 (Exception):** 링크를 갱신하지 않거나, 렌더 산출물을 직접 편집하거나, 배포 설정을 문서 폴더에 섞어 넣는 경우

## 5. 핵심 구성요소 (Building Blocks)

* **레고 블록 1 (`apps/`):** 실행 가능한 애플리케이션을 둔다. 현재는 MkDocs 사이트 빌더가 여기에 속한다.
* **레고 블록 2 (`content/`):** 사람이 읽는 모든 문서의 루트다. 출판 소스, 파생 산출물, 보관 문서, 프롬프트, 메모, 리서치를 편집 규칙별로 나눈다.
* **레고 블록 3 (`infra/`, `src/`, `dist/`):** 운영 설정, 실행 코드/스크립트, 빌드 산출물의 경계를 분리한다.
* **서로 어떻게 맞물려 돌아가는가?:** `apps/docs-site`는 `content/docs`를 읽어 사이트를 만들고, 자동화 코드는 `src/`에서 실행되며, 결과물은 `dist/`에 쌓인다. 인프라 배포 설정은 `infra/`에 남아 문서와 실행 경로를 오염시키지 않는다.

## 6. 상태 전이 (State Transition)

*상태가 어떻게 변하는지 흐름을 한눈에 보여줍니다. (표 안의 문장은 짧고 직관적으로!)*

| 초기 상태 | 이벤트 (트리거) | 전이 조건 | 변경 후 상태 | "바뀐 걸 어떻게 알지?" (관찰 방법) |
| :--- | :--- | :--- | :--- | :--- |
| `MIXED_ROOT` | 저장소 구조 감사 | 문서/코드/인프라/산출물 경계가 섞임 | `DOMAIN_MAPPED` | 5개 최상위 도메인 표 작성 |
| `DOMAIN_MAPPED` | 파일 이동 계획 수립 | 링크와 CI 파손 위험을 고려함 | `STAGED_MIGRATION` | 복사 후 구 경로 단계적 제거 계획 |
| `STAGED_MIGRATION` | 빌드와 검증 실행 | MkDocs, CI, 자동화 스크립트가 새 경로 사용 | `ACCEPTED_LAYOUT` | 검증 기준 체크리스트 통과 |

## 7. 불변식 (Invariant: 절대 깨지면 안 되는 규칙)

* **하늘이 무너져도 지켜야 할 조건:** 파일 위치는 아티팩트의 성격과 편집 권한을 드러내야 한다.
* **이게 깨지면 생기는 대참사:** 기여자가 렌더 산출물을 직접 고치거나, 배포 설정을 문서 소스처럼 다루거나, CI가 오래된 경로를 참조해 배포가 깨질 수 있다.
* **수수방관 금지 (검증법):** MkDocs 빌드, CI 경로 검증, extra 자산 동기화, Rust 문서 검증기를 구조 변경 후 반드시 실행한다.

## 8. 가장 작은 예제 (Minimal Viable Example)

* **뇌컴파일이 가능한 수준의 인풋:** `docs/`, `docker/`, `configs/`, `ansible/`, `code/`, `scripts/`, `site/`가 루트에 흩어진 저장소를 상상한다.
* **한 스텝씩 뜯어보기:** 파일 목적을 먼저 판정한다. 문서 출판 소스는 `content/docs/`, 사이트 빌더는 `apps/docs-site/`, 배포 설정은 `infra/`, 자동화 스크립트는 `src/automation/`, 빌드 결과는 `dist/site/`로 보낸다.
* **해피 엔딩 (결과):** 새 문서를 추가할 때는 `content/docs/<category>/`만 보면 되고, 실행 코드나 배포 설정을 문서 폴더에서 찾느라 헤매지 않는다.

```text
apps/     -> 실행 가능한 애플리케이션
content/  -> 사람이 읽는 모든 문서
infra/    -> 배포 및 운영 설정
src/      -> 실행 가능한 코드와 스크립트
dist/     -> 빌드 산출물
```

## 9. 실패 사례 (What could go wrong?)

* **폭망 시나리오 1:** 기존 링크를 새 경로로 갱신하지 않아 GitHub Raw URL이나 내부 문서 링크가 깨진다.
* **폭망 시나리오 2:** `content/rendered/`의 파생 산출물을 직접 편집해서 원본과 결과물이 서로 달라진다.
* **폭망 시나리오 3:** 전면 일괄 이동으로 CI, MkDocs 설정, 자동화 스크립트가 동시에 실패한다.
* **범인 검거 (어떤 불변식이 깨졌나?):** 파일 위치가 아티팩트 성격과 편집 권한을 드러내야 한다는 7번 불변식이 깨진 것이다.

## 10. 뇌 확장하기 (Evolution & Variants)

* **조건을 살짝 바꾸면?:** 문서 사이트가 여러 개로 나뉘면 `apps/` 아래에 사이트 앱을 추가하고, 공통 콘텐츠와 사이트별 콘텐츠를 다시 분리해야 한다.
* **비슷한 놈들과 계급장 떼고 비교하기:** 모노레포의 `apps/packages/docs` 구조와 비슷하지만, 이 저장소는 패키지보다 문서 출판과 운영 자산 경계를 우선한다.
* **다른 데서 써먹기:** 개인 지식 저장소, 홈랩 운영 문서, 회사 내부 런북 저장소에서도 "사람이 읽는 문서", "실행 코드", "배포 설정", "산출물"을 먼저 나누는 기준으로 쓸 수 있다.

## 11. 최종 체크리스트 (Definition of Done)

*글 작성 후 아래 항목을 채웠는지 확인하는 셀프 검토용 목록이다.*

- [x] 1초 만에 이해하는 한 문장 요약이 있는가?
- [x] 일목요연한 상태 전이 표를 채웠는가?
- [x] 머릿속 그림을 표현한 구조도(다이어그램)가 포함되었는가?
- [x] 직접 굴려본 실습 결과(코드/로그)를 첨부했는가?
- [x] 에러를 마주하고 해결한 오답 노트가 있는가?
- [x] 주니어 동료에게 막힘없이 설명할 수 있는 수준인가?

검증 명령:

```bash
cd apps/docs-site && mkdocs build --clean
cargo test --manifest-path src/tools/docs-validator-rs/Cargo.toml
```

## 12. 뇌에 새기는 복습 문장 (TL;DR Blank)

*복습 시 이 문장만 보고도 핵심을 떠올릴 수 있도록 빈칸을 채운다.*

> 이 개념은 결국 **문서, 코드, 인프라 설정, 빌드 산출물이 한 저장소에서 뒤섞이는 문제**를 해결하기 위해 태어났고,
> 우리가 계속 감시해야 할 핵심 상태는 **파일 위치와 편집 권한** 이며,
> **새 파일을 추가하거나 기존 파일을 이동하는** 조건이 발동할 때 상태가 바뀐다.
> 그리고 무슨 일이 있어도 **파일 위치는 아티팩트의 성격과 편집 권한을 드러내야 한다** 라는 불변식은 반드시 유지되어야만 한다!
