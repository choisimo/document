# 트랜잭션과 동시성 검증

트랜잭션은 여러 데이터 변경을 하나의 논리 작업으로 묶는다. 원자성, 일관성, 격리성, 지속성은 서로 다른 질문에 답하며, 특정 DBMS의 기본 격리 수준이나 장애 시 결과는 제품·설정·실험으로 확인해야 한다.

| 속성 | 확인할 질문 |
| --- | --- |
| 원자성 | 중간 실패 시 트랜잭션 안의 변경이 함께 rollback되는가? |
| 일관성 | 업무 규칙과 schema 제약이 유효 상태를 유지하는가? |
| 격리성 | 동시에 실행한 작업 사이에서 어떤 읽기·충돌을 허용하는가? |
| 지속성 | 성공으로 응답한 commit을 어떤 장애 조건까지 보존하는가? |

## 업무 조건과 동시 변경

**예시:** 재고가 1일 때 두 요청이 동시에 “재고 확인 후 1 차감”을 수행한다. 조회와 변경을 각각 잘 작성해도 둘이 같은 재고를 관찰할 수 있다. 필요한 불변식은 재고가 음수가 되지 않고 실제 확보한 요청만 성공하는 것이다.

해결을 평가할 때에는 DB 제약, 조건부 갱신과 영향 행 수, 잠금 또는 낙관적 버전 검사, 트랜잭션 경계를 함께 확인한다. 특정 SQL 한 줄을 모든 엔진에서 같은 동시성 보장으로 해석하지 않는다.

## 격리 수준 이름만으로 부족한 이유

Read Committed, Repeatable Read, Serializable 등의 이름은 출발점이다. 일반 조회·잠금 조회, 범위 조건, 인덱스, MVCC와 충돌 처리에 따라 실제 실행이 달라진다. 잠금은 대기·교착을 만들 수 있고, MVCC도 모든 쓰기 충돌이나 자원 비용을 없애지 않는다.

서로 다른 두 연결로 아래 순서를 기록한다.

1. 두 연결의 자동 커밋과 격리 설정, 초기 데이터 상태를 고정한다.
2. 첫 작업의 읽기 또는 잠금 후 두 번째 작업을 진행한다.
3. 어느 시점에 대기·실패·commit하는지 기록한다.
4. 최종 데이터와 성공 응답 수가 업무 불변식과 일치하는지 확인한다.
5. 강제 오류·교착 또는 직렬화 실패 뒤 rollback과 재시도 결과를 확인한다.

## 재시도와 외부 부작용

트랜잭션 재시도는 업무 단위와 횟수·시간 제한을 정해야 한다. DB rollback이 이미 발송한 이메일이나 외부 API 호출까지 취소해 주지는 않는다. DB 밖의 부작용과 중복 억제는 별도의 설계·검증 대상이다.

commit 도중 연결이 끊기면 클라이언트가 결과를 모를 수 있다. 단순 재시도 전에 업무 식별자로 이미 반영됐는지 확인할 수 있는 계약이 필요하다. “응답을 못 받음”과 “반영되지 않음”을 같은 상태로 기록하지 않는다.

완료 증거에는 DBMS·버전·설정, 두 세션의 실행 순서, 오류, 최종 데이터, 재시도 결과가 포함된다. 이 페이지는 운영 DB에서 동시 실행 시험을 했다는 보고서가 아니다.
