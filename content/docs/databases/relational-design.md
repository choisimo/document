# 관계형 모델과 함수 종속성·정규화

정규화는 테이블 개수를 늘리는 절차가 아니라 데이터가 만족해야 할 종속성을 기준으로 갱신 이상을 줄이는 설계다. 이 문서는 보관된 DB 이론에서 개념과 검증 방법을 복구했다. 실제 서비스 스키마나 migration은 제시하지 않는다.

## 관계는 제약으로 표현한다

기본 키는 행을 식별하고 외래 키는 참조 가능한 값을 제한한다. `1:N`과 `N:1`은 바라보는 방향이 다르다. 외래 키 하나만으로 `1:1`이 되는 것은 아니며 유일성 제약을 함께 확인해야 한다. 필수 관계인지 여부는 null 허용과 별개로 정한다. `N:M` 관계는 연결 테이블과 그 행의 유일성으로 표현할 수 있다.

JPA 어노테이션 설명과 실제 DB 제약은 [연관관계 안내](jpa/relationships.md)에서 함께 확인한다.

## 함수 종속성과 후보 키

`X → Y`는 같은 X 값을 갖는 행은 Y 값도 같아야 한다는 업무 제약이다. 현재 샘플에 우연히 중복이 없다고 이 제약이 성립하는 것은 아니다. 후보 키는 모든 속성을 결정하는 최소 속성 집합이다.

다음은 **가상의 상품 주문 예시**다.

```text
OrderLine(order_id, product_id, product_label, quantity)
가정:
  (order_id, product_id) → quantity
  product_id → product_label
후보 키:
  (order_id, product_id)
```

상품명을 여러 주문 행에 반복하면 이름 수정 시 일부만 바뀔 수 있다. 다음처럼 분해하면 상품명의 정본을 한곳에 둔다.

```text
Product(product_id, product_label)
OrderLine(order_id, product_id, quantity)
```

이 예시는 주문 시점의 상품명이 아니라 현재 상품명을 참조한다는 가정이다. 구매 당시 표시명을 보존해야 한다면 별도의 요구와 모델이 필요하다.

## 정규형을 판정하는 순서

| 기준 | 확인할 내용 |
| --- | --- |
| 1NF | 정한 도메인에서 속성 값과 반복 그룹을 어떻게 표현하는지 |
| 2NF | 후보 키 일부에만 종속하는 비주요 속성이 있는지 |
| 3NF | 비자명 FD에서 결정자가 superkey이거나 종속 속성이 주요 속성인지 |
| BCNF | 모든 비자명 FD의 결정자가 superkey인지 |

분해 후에는 원래의 유효 관계를 조인으로 정확히 복원할 수 있는 **무손실성**과 원래 FD를 분해된 테이블의 제약으로 검사할 수 있는 **종속성 보존**을 각각 확인한다. 높은 정규형이라는 이름만으로 둘 다 만족한다고 말하지 않는다.

완료 증거는 속성 집합, 업무 FD, 후보 키 도출, 위반 FD, 분해 결과, 두 검증 결과다. 성능 때문에 중복을 다시 도입한다면 갱신 주체·불일치 감지·복구 규칙과 실제 측정 근거를 추가한다.
