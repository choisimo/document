# 쿼리 I/O와 인덱스 관찰

같은 SQL도 데이터 분포, 통계, 캐시, 인덱스, 엔진 버전에 따라 다른 계획으로 실행될 수 있다. 이 문서는 보관 노트의 개념을 복구하되 출처를 확인할 수 없는 지연 수치와 보편적인 캐시 공식은 사용하지 않는다.

## 논리 읽기와 물리 읽기

논리 읽기는 엔진이 필요한 페이지에 접근하는 관점이고 물리 읽기는 캐시에 없는 페이지를 아래 저장 계층에서 가져오는 관점이다. 정확한 counter 정의와 운영체제 캐시·read-ahead의 포함 여부는 엔진별로 확인한다.

같은 데이터를 두 번 읽어 두 번째 실행이 빨라졌다면 캐시 영향일 수 있다. 쿼리가 더 적은 일을 하게 됐는지 판단하려면 행 수, 반복 횟수, 페이지 접근, 실제 실행 시간을 함께 본다. 운영 서버의 캐시를 임의로 비워 실험하지 않는다.

## 인덱스 선택의 조건

| 접근 | 적합성을 판단할 근거 |
| --- | --- |
| 순차 스캔 | 읽을 행 비율, 데이터 크기, 연속 읽기 비용 |
| 정렬된 트리 인덱스 | 동등·범위 조건, 정렬 요구, 선택도, 추가 테이블 접근 |
| 해시 기반 접근 | 지원 엔진의 동등 비교와 충돌·확장 방식 |
| covering 접근 | 필요한 컬럼을 인덱스에서 얻는지, 인덱스 크기·쓰기 비용 |

인덱스는 저장 공간과 쓰기 유지 비용을 추가한다. “인덱스 사용” 표시만으로 빨라졌다고 결론 내리지 않는다. 교재의 dense·sparse 구분과 제품의 clustered·secondary 구현 용어도 실제 저장 구조에 맞춰 연결한다.

## EXISTS와 조인

`EXISTS`는 조건을 만족하는 행의 존재 여부를 표현한다. 결과에 오른쪽 행 자체가 필요한 조인과 요구가 다르다. 옵티마이저는 이 의도를 다른 물리 계획으로 바꿀 수 있으므로 `EXISTS`라는 단어만으로 디스크 읽기 횟수나 항상 빠른 결과를 보장하지 않는다.

비교할 때에는 두 SQL의 결과 의미가 같은지 먼저 확인한다. 중복·NULL·일치하지 않는 행 때문에 결과가 달라지면 성능 비교 자체가 다른 문제를 비교한 것이다.

## 재현 가능한 관찰 기록

DBMS와 버전, schema, 인덱스 정의, 데이터 건수·분포, parameter, 실행 계획, 실제 행 수·반복, 캐시 조건과 반복 측정을 남긴다. 실행을 수반하는 분석 옵션은 쓰기 쿼리에서 데이터 변경을 일으킬 수 있으므로 선택한 엔진의 옵션부터 확인한다.

예상과 실제 행 수 차이가 크면 통계·상관관계·매개변수 분포를 확인한다. 물리 읽기가 줄어도 CPU·잠금·네트워크가 병목이면 지연은 줄지 않을 수 있다. 최적화 완료는 결과 동일성과 실제 업무 지표의 개선을 함께 확인한 상태다.
