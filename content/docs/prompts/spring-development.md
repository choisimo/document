# Spring 개발 요청 프롬프트

보관된 두 Spring 프롬프트는 여러 DB·캐시·메시징 기술을 한꺼번에 지정하고 코드만 출력하도록 요구한다. 재사용할 때에는 실제 프로젝트에서 확인한 기술과 필요한 변경만 넣고 검증 결과를 별도로 요청한다.

## 요청 템플릿

```text
기능: <구체적인 사용자 동작과 결과>
정본: <실제 빌드·설정·코드 경로와 revision>
버전: <build 파일에서 확인한 Java·Spring·라이브러리>
현재 데이터 저장소: <확인한 것만>
변경 범위: <파일 또는 모듈>
제외 범위: <관련 없는 앱·설정·배포>

현재 controller·service·repository·schema를 먼저 읽어라.
입력 검증, 인증·권한, 트랜잭션 경계와 오류 응답을 명시하라.
목록 조회는 실제 요구에 맞는 정렬·페이지 계약을 보존하라.
새 캐시·DB·메시지 broker를 근거 없이 추가하지 마라.
실제 query와 계획·측정 없이 N+1 또는 성능 해결을 주장하지 마라.
설정에는 비밀값 대신 주입 경로와 필수 여부를 적어라.
변경 파일과 검증 명령·결과·실행하지 못한 항목을 보고하라.
```

## 데이터·실패 계약 보충

동시에 같은 요청이 들어올 때의 결과, 외부 서비스 실패, 재시도와 중복 처리, 트랜잭션 밖의 부작용을 입력에 추가한다. 여러 저장소를 사용한다면 어느 데이터의 정본이 어디인지와 부분 실패에서의 복구를 먼저 설명한다.

“모든 코드 포함”은 대상이 없는 무한한 요구다. 대표 흐름과 수용 조건, 실행 가능한 빌드·검사 범위를 지정한다. 코드 예시만 요청했다면 실행된 production 구현과 구분하도록 표시한다.

## 결과 수용

실제 파일·등록 경로·의존성 버전을 확인하고 대표 성공·권한 거부·입력 오류·중복·외부 실패를 검증한다. 실행하지 않은 integration test를 통과한 것으로 표시하지 않는다. 설명·테스트 증거가 필요한 작업에서는 “코드만 출력” 형식을 적용하지 않는다.

근거: `content/prompts/SPRINGBOOT_PROMPT.txt`, `SPRINGBOOT_PROMPT2.txt`의 기술 스택·품질·출력 요구. 설계 배경은 [Spring 경계](../development/spring-architecture.md), [API 계약](../development/api-contracts.md).
