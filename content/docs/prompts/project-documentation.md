# 근거 기반 프로젝트 문서화 프롬프트

프로젝트 문서화에는 독자·범위·정본·제외 항목이 먼저 필요하다. 프롬프트만으로 저장소 접근이나 실행 능력이 생기지 않는다. 읽지 못한 소스는 빈칸을 추측해 채우지 않고 미확인으로 남긴다.

## 입력 템플릿

다음은 **재사용 예시**다. 실제 비밀이나 개인 경로를 붙여 넣지 않는다.

```text
목표: <독자가 수행할 작업>
독자: <개발자 / 운영자 / 기여자>
대상 revision: <확인한 식별자>
허용 소스: <경로 목록과 우선순위>
현재 구현의 근거: <코드·설정·테스트·실행 로그의 위치>
제외: 비밀, 개인 식별자, 내부 주소, 전체 내부 연결도, 생성 산출물
작업 권한: <읽기 / 문서 편집 / 허용된 검사>
출력: <문서 종류와 경로>

먼저 실제 소스를 읽고 목록을 작성하라.
각 주장을 확인된 사실, 예시, 제안, 미확인 항목으로 구분하라.
존재하는 endpoint·필드·symbol은 실제 등록과 선언으로 확인하라.
명령에는 작업 위치·입력·출력·실패 조건·검증 범위를 적어라.
실행하지 않은 검사를 성공했다고 쓰지 마라.
누락 요구와 제외 사유를 문서 끝의 coverage 표로 남겨라.
```

## 필요한 문서만 선택

| 문서 | 확인할 근거 |
| --- | --- |
| 아키텍처 | 실제 entrypoint, 경계, 의존 방향, 공개 가능한 데이터 흐름 |
| API·데이터 계약 | 등록 코드, DTO·schema, 권한, 오류·부작용 |
| 실행·배포 안내 | 고정된 의존성, 명령, 출력, 환경 주입 |
| 운영 런북 | 관찰할 상태, 실패 지점, 복구 조건·증거 |
| 기여 안내 | 정본 위치, 변경 규칙, 검사 범위 |

원본 프롬프트의 긴 목차를 모든 프로젝트에 강제하지 않는다. API가 없는 라이브러리에 controller 문서를 만들거나 사용하지 않는 DB를 기술 스택에 추가하지 않는다.

## 결과 검토

문서의 경로·symbol·설정 키를 원본과 다시 대조한다. 각 요구사항이 어느 절에서 충족되는지 확인하고, 구현·제안·예시가 섞이지 않았는지 읽는다. 원문 코드의 의미, 인용, front matter, 링크를 보존한다.

문법·링크 검사와 사실 검증은 별개다. 특정 품질 점수·생산성 개선율·완료율은 측정이 없으면 적지 않는다. 다음 작업자가 다시 확인할 수 있도록 실행 명령·종료 코드·남은 불확실성을 남긴다.
