# Compose 스택 검토와 복구

`infra/docker/stacks/`는 서비스별 Compose 예시 모음이다. [스택 목록](../../extra/docker/stacks/index.md)에서 주제를 찾고 해당 디렉터리의 README와 실제 Compose 파일을 함께 읽는다. 목록의 서비스 수와 이미지명은 설정 메타데이터이며 실행 상태가 아니다.

## 실행 전에 고정할 입력

이미지 태그·digest, Compose 버전, 실제 환경 파일, 저장 경로, UID/GID, 게시 포트, 초기화 스크립트의 적용 조건을 확인한다. 여러 `compose*.yml` 파일이 있으면 어떤 파일과 override를 사용할지 먼저 선택한다. `.env.example`의 존재는 안전한 기본값이나 완전한 구성을 보증하지 않는다.

승인한 실험 경로에서 다음 형태로 설정을 검사한다. 환경 파일은 저장소 밖에서 관리하고, 값 전체가 출력되는 명령 결과를 공유하지 않는다.

```bash
docker compose --env-file '<LOCAL_ENV_FILE>' -f '<COMPOSE_FILE>' config --quiet
```

`config --quiet` 성공은 구성 파싱·보간 확인이다. 이미지의 환경 변수 지원, 인증, 데이터베이스 준비, 실제 요청 성공까지 검증하지 않는다.

## 소스별로 다른 데이터 계약

| 예시 스택 | 별도로 확인할 사항 |
| --- | --- |
| MariaDB | backup 서비스 선언과 독립된 DB 복원 성공을 구분 |
| MongoDB | replica-set 설정만으로 다중 장애 영역이나 선출 성공을 보증하지 않음 |
| `supabase` 디렉터리 | PostgreSQL·pgvector·PostgREST 부분 예시. 전체 Supabase 서비스 집합이 아님 |
| n8n | worker의 DB·큐·암호화 설정 일치, 재시도·중복 실행, 자격증명 복구 |
| Langflow | 초기 볼륨 소유권, DB migration, 저장한 flow의 재시작 후 보존 |
| 파일 공유 스택 | 파일과 메타데이터를 함께 복원. 공유 링크 만료와 삭제·보존 정책 구분 |
| VPN을 사용하는 미디어 스택 | 터널 정상·중단 상태에서 각각 송신 경로와 누출 여부 확인 |

이 구분은 각 스택 README의 계약을 묶은 것이다. 실제 이미지 지원 상태나 현재 배포 결과를 대신하지 않는다.

## 관찰과 완료 기준

대상 스택을 적용할 권한과 복구 사본을 확보한 후, 실행한 것과 동일한 파일·프로젝트 옵션으로 `ps`, 제한된 `logs`, 서비스가 제공하는 readiness를 확인한다. 이어 인증이 필요한 대표 쓰기·읽기 한 건과 재시작 후 보존을 시험한다. 로그에는 원문 데이터나 자격증명을 남기지 않는다.

컨테이너가 반복 재시작하면 첫 실패 로그, exit code, mount 권한, DB 연결과 migration 상태를 확인한다. 데이터 디렉터리 초기화로 증상을 숨기지 않는다. 초기화 스크립트가 빈 볼륨에서만 동작하는지 확인한다.

## 백업과 되돌리기

백업에는 DB 일관성, 파일, 설정, 복호화에 필요한 비밀의 별도 보관이 포함돼야 한다. 운영 데이터와 분리된 위치에 복원해 대표 레코드·파일·권한을 확인한다. 파일이 생성됐거나 압축 해제가 됐다는 사실만으로 복원 성공으로 표시하지 않는다.

버전 교체 후 실패하면 이전 이미지·설정과 DB 스키마의 호환성을 확인한다. 데이터 migration이 되돌릴 수 없는 경우에는 이전 이미지만 다시 실행하는 것으로 복구되지 않는다. `down --volumes`나 전체 Docker 정리는 일반적인 장애 복구 절차로 사용하지 않는다.
