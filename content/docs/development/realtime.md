# SSE와 WebSocket 연결 수명

SSE와 WebSocket은 HTTP 요청·응답 한 번으로 끝나지 않는 실시간 흐름에 쓰인다. 이 문서는 보관된 Spring·브라우저 RTC 자료에서 전송과 운영 계약을 복구했다. 특정 라이브러리 버전의 완성된 서버 코드를 제공하지 않는다.

| 기준 | SSE | WebSocket |
| --- | --- | --- |
| 주된 흐름 | 서버가 클라이언트에 이벤트 전송 | 연결 양쪽에서 메시지 전송 |
| 응용 예 | 작업 진행·알림 스트림 | 양방향 협업·메시지 교환 |
| 복구 설계 | 이벤트 ID·재전송 범위·중복 처리 | 재연결·재구독·미수신 메시지 복구 |
| 공통 확인 | 인증·만료·프록시 timeout·느린 소비자 | 인증·만료·프록시 timeout·느린 소비자 |

연결이 재성립됐다는 사실과 끊어진 사이의 메시지를 복구했다는 사실은 다르다. 어떤 전송 방식도 이름만으로 exactly-once 업무 처리를 보장하지 않는다.

## 상태와 자원 정리

```text
연결 요청 → 인증·권한 확인 → 활성 연결
활성 연결 → 메시지 전달 또는 timeout·오류·종료
종료 → 서버 자원 정리 → 허용된 재연결·재구독
```

Spring의 emitter나 WebSocket session을 컬렉션에 보관한다면 정상 종료·timeout·전송 오류에서 제거하는 경로를 확인한다. 단일 프로세스의 세션 목록은 다른 서버 인스턴스에 연결된 클라이언트를 포함하지 않는다. 서버를 늘리기 전에 이벤트 분배와 구독 소유권을 설계해야 한다.

## 프록시와 클라이언트 확인

프록시가 스트림을 버퍼링하거나 idle timeout으로 끊는지, 헤더·연결 upgrade가 필요한 흐름에 전달되는지 확인한다. 긴 timeout만 늘리면 죽은 연결과 느린 소비자가 자원을 점유할 수 있다. heartbeat와 재연결 backoff도 실제 정책으로 검증한다.

브라우저 탭 닫기, 네트워크 단절, 인증 만료, 서버 재시작을 각각 시험한다. 도착 순서·이벤트 식별자·중복·누락·대기열 한도를 기록하고, 사용자가 다시 접속했을 때 어떤 상태를 보여 줄지 정한다.

채팅처럼 양방향이라고 반드시 WebSocket만 가능한 것은 아니며, 서버 알림이라고 SSE가 모든 환경에서 최선인 것도 아니다. 필요한 방향성, 브라우저·인증 방식, 프록시, 메시지 크기와 운영 비용으로 선택한다.

## 완료 증거

연결 성공 외에 종료 후 자원 회수, 다중 인스턴스 전달, 권한 없는 구독 거부, 재연결 중복 억제와 누락 복구를 확인한다. 공개 보고서에는 사용자 메시지나 세션 자격증명을 담지 않는다.
