# React 상태와 정적 빌드 경계

보관된 React 자료는 여러 상태 관리 방식의 학습 초안이다. 여기서는 라이브러리의 인기나 오래된 scaffold 명령 대신 상태의 책임과 기존 프로젝트의 빌드 계약을 복구한다. Documentation Hub의 현재 셸이 React로 구현됐다는 뜻은 아니다.

## 상태를 먼저 분류한다

| 상태 | 예시 | 소유권·수명 |
| --- | --- | --- |
| 로컬 UI | 입력 중인 문자열, 대화상자 열림 | 해당 컴포넌트와 사용자 작업 |
| 공유 클라이언트 | 여러 화면에서 편집하는 임시 선택 | 명시한 기능 경계와 변경 이벤트 |
| 서버 데이터 | API에서 가져온 문서 목록 | 서버 정본, 클라이언트 캐시·재검증 |
| URL | 필터, 페이지, 선택 탭 | 링크 공유와 뒤로 가기 |
| 파생 값 | 필터링된 목록, 합계 | 다른 상태에서 계산. 별도 저장 필요성 검토 |

두 곳에 같은 값을 저장하면 갱신 순서를 맞춰야 한다. state를 어디에 둘지 결정하기 전에 정본과 계산 가능한 값을 나눈다. 서버 응답에는 로딩·오류·신선도·취소 상태를 붙이고 늦게 도착한 응답이 새 화면을 덮지 않게 한다.

낙관적 갱신은 성공 화면을 먼저 보여 주는 정책이다. 실패 시 되돌릴 데이터와 후속 변경의 처리, 중복 요청의 의미를 정해야 한다. localStorage에 넣을 때에는 보존 기간·삭제·공유 기기에서의 노출을 별도로 판단한다.

## 기존 프로젝트 빌드

`package.json`의 scripts, lockfile, `engines`, CI 설정을 먼저 읽는다. 기존 앱을 빌드하려고 새 scaffold를 생성하지 않는다. 다음 명령은 **npm과 build script를 사용하는 대상 프로젝트에서만** 실행한다.

```bash
node --version
npm --version
npm run
npm ci
npm run build
```

출력 디렉터리는 build 도구 설정으로 확인한다. 모든 프로젝트가 `build/` 또는 `dist/`를 사용한다고 가정하지 않는다. 서버 실행이 필요한 framework 기능이 있으면 정적 파일 호스팅만으로 동작하지 않을 수 있다.

## 결과 확인과 복구

루트 URL뿐 아니라 하위 경로 직접 접속·새로고침, JS·CSS URL, 이미지, 오류 화면을 확인한다. 클라이언트 라우팅 fallback과 실제로 없는 정적 자산의 404를 구분한다. 브라우저가 내려받는 번들에는 비밀을 넣지 않는다.

이전 산출물과 입력 revision을 보존하고 묶음 전체를 교체한다. 일부 JS만 되돌리면 다른 파일·캐시와 버전이 어긋날 수 있다. 완료 기록에는 설치·빌드 종료 코드와 대표 사용자 동작, 배포 경로, rollback 대상을 남긴다.
