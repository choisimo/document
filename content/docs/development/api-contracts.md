# API 계약 불일치 감지

API 계약은 파일 하나의 존재가 아니라 실제 요청·응답·권한·부작용에 대한 약속이다. 보관 노트의 OpenAPI·타입 생성·계약 테스트 제안을 복구한 안내이며, 이 저장소에 그 테스트 파이프라인이 설치돼 있다는 뜻은 아니다.

## 무엇을 맞춰야 하는가

| 비교 대상 | 찾을 수 있는 불일치 | 이 검사만으로 알 수 없는 것 |
| --- | --- | --- |
| 이전 명세 ↔ 새 명세 | 필수 필드 추가, 타입·경로 변경 | 실제 서버가 명세를 지키는지 |
| 명세 ↔ 생성 타입·클라이언트 빌드 | 없는 속성 참조, 재생성 누락 | 런타임 값·권한·업무 의미 |
| 서버 응답 ↔ schema | 응답 필드·형식·상태 불일치 | 모든 소비자의 기대 |
| 소비자 계약 ↔ provider 실행 | 대표 요청·응답 기대 위반 | 기록하지 않은 흐름과 장애 |

**예시:** 응답의 `itemId`를 `item_id`로 바꾸면 값이 같아도 기존 클라이언트가 필드를 읽지 못할 수 있다. 필드명뿐 아니라 null 허용, 열거값, 날짜 형식, 오류 응답과 정렬·페이지 경계도 계약이다.

## 적용 절차

1. 대상 API의 실제 등록 경로와 handler를 찾고, 정본 명세의 위치·버전을 기록한다.
2. 인증, 권한, 입력 제약, 성공·실패 응답과 저장 부작용을 대표 요청에서 추적한다.
3. 명세 diff 도구와 생성 도구의 버전을 고정하고 실패 종료 코드가 검사에 반영되는지 확인한다.
4. 의도적으로 깨지는 작은 변경을 시험해 필수 검사가 실패하는지 확인한다. 성공 사례만으로 감지 능력을 주장하지 않는다.
5. 실제 provider와 소비자 흐름을 검증하고 재시도·중복 요청·외부 실패를 포함한다.

응답 검증 middleware를 추가할 때에는 검사 실패 시 상태·본문·로그와 성능 영향을 정한다. 내부 오류나 원본 요청 내용을 그대로 공개 응답·로그에 넣지 않는다.

## 호환 변경과 완료 증거

변경을 소비자 전체에 동시에 적용할 수 없다면 구 계약과 새 계약의 공존 기간, 읽기·쓰기 전환, 제거 조건을 정한다. 명세 변경, 타입 재생성, 소비자 빌드, 실제 실행 결과는 별개 증거로 남긴다.

이 안내의 예시 경로나 도구명을 대상 프로젝트의 실제 파일·등록 코드 대신 인용하지 않는다. 근거가 없으면 도입 제안으로 남긴다.
