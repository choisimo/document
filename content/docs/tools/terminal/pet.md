# Pet

`pet`은 자주 쓰는 긴 명령어를 스니펫으로 저장하고 검색해서 재사용하는 CLI 도구다. 기억하기 어려운 옵션 조합, 서버 점검 명령, 반복적인 Git 명령을 개인 명령어 노트처럼 관리할 수 있다.

## 1. 왜 필요한가? (Pain Point & Motivation)

긴 명령어를 셸 히스토리에서 다시 찾거나 문서에서 복사하면 실수가 생기기 쉽다. 특히 `docker`, `kubectl`, `rsync`, `find`, `ffmpeg`처럼 옵션이 긴 명령은 한 글자 차이로 결과가 크게 달라질 수 있다.

`pet`의 목적은 "자주 쓰지만 외우기 싫은 명령"을 검색 가능한 스니펫으로 만들고, 실행 전에 내용을 확인하게 하는 것이다.

## 2. 현재 나의 상태 (Baseline)

다음 상태라면 `pet`을 도입할 가치가 있다.

- 긴 명령어를 메모 앱, README, 셸 히스토리에 흩어 저장한다.
- `history | grep`으로 매번 예전 명령을 찾는다.
- 위험한 옵션이 포함된 명령을 복사하면서 대상 경로만 바꾼다.
- 서버마다 다른 점검 명령을 기억하지 못한다.
- 명령 설명과 명령 본문을 함께 관리하고 싶다.

## 3. 도달하고 싶은 목표 (Target State)

잘 관리되는 스니펫 저장소는 다음 상태를 만족한다.

- 스니펫마다 설명, 명령 본문, 태그가 있다.
- 파괴적 명령은 실행 전 확인 문구나 dry run 버전을 먼저 둔다.
- 비밀번호, 토큰, 개인키 경로 같은 민감 정보는 스니펫에 직접 넣지 않는다.
- 로컬 전용 스니펫과 공유 가능한 스니펫을 분리한다.
- 동기화 기능을 쓰더라도 공개 범위와 저장 위치를 확인한다.
- `fzf` 같은 퍼지 검색 도구와 연결해 빠르게 찾을 수 있다.

## 4. 시스템 번역 (Data Flow)

`pet` 사용 흐름은 다음과 같다.

```text
명령 작성
  -> pet new
  -> 설명과 태그 저장
  -> pet search
  -> 후보 선택
  -> 명령 확인
  -> 실행 또는 편집
```

중요한 경계는 "검색"과 "실행" 사이에 있다. 스니펫 도구는 명령을 쉽게 실행하게 만들기 때문에, 삭제·배포·권한 변경 명령은 선택 직후 바로 실행하지 않고 내용을 다시 확인해야 한다.

## 5. 핵심 구성요소 (Building Blocks)

- Snippet: 저장된 명령어 본문이다.
- Description: 스니펫을 검색할 때 보이는 설명이다.
- Tag: `docker`, `git`, `network`, `danger`처럼 묶는 분류다.
- Search UI: `pet search`에서 후보를 고르는 화면이다.
- Editor: `pet edit`로 스니펫 파일을 직접 정리할 때 사용하는 편집기다.
- Sync: Gist 같은 외부 저장소와 스니펫을 동기화하는 기능이다.
- Shell integration: 선택한 스니펫을 현재 셸 입력줄에 넣거나 실행하는 흐름이다.

## 6. 상태 전이 (State Transition)

스니펫은 다음 상태로 관리한다.

```text
draft
  -> saved
  -> reviewed
  -> used
  -> updated
  -> archived
```

- `draft`: 아직 검증되지 않은 명령이다.
- `saved`: `pet new`로 저장됐다.
- `reviewed`: 설명, 태그, 위험도, 변수 위치를 확인했다.
- `used`: 실제 작업에서 사용했다.
- `updated`: 옵션이나 대상 환경 변화에 맞게 수정했다.
- `archived`: 더 이상 쓰지 않지만 참고용으로 보관한다.

운영 명령은 `draft` 상태에서 바로 실행하지 않는다. 먼저 작은 대상이나 dry run으로 검증한다.

## 7. 불변식 (Invariant: 절대 깨지면 안 되는 규칙)

- 스니펫에는 실제 비밀번호, 토큰, API 키를 저장하지 않는다.
- `rm`, `mkfs`, `dd`, `rsync --delete`, 배포 명령은 `danger` 태그를 붙인다.
- 파괴적 명령에는 dry run 또는 대상 확인 명령을 함께 저장한다.
- 동기화 대상이 공개 Gist인지 비공개 저장소인지 확인한다.
- 서버별 경로와 사용자명은 변수처럼 눈에 띄게 표시한다.
- 스니펫 실행 전 현재 디렉터리와 대상 호스트를 확인한다.
- 오래된 스니펫은 주기적으로 실행 가능 여부를 점검한다.

## 8. 가장 작은 예제 (Minimal Viable Example)

설치는 배포판 패키지나 공식 GitHub 릴리즈에서 현재 버전을 확인해 진행한다. `fzf`가 있으면 검색 경험이 좋아진다.

```bash
pet new
pet list
pet search
pet edit
```

저장하기 좋은 스니펫 예시는 다음과 같다.

```bash
find ./logs -type f -name "*.log" -mtime +30 -print
```

삭제 명령은 바로 저장하지 말고 확인 명령과 분리한다.

```bash
find ./logs -type f -name "*.log" -mtime +30 -delete
```

설명은 다음처럼 실행 의도가 드러나야 한다.

```text
tag: logs,danger
description: 30일 지난 로그 파일 삭제 전 대상 확인 후 삭제
```

## 9. 실패 사례 (What could go wrong?)

- 스니펫에 실제 서버 비밀번호나 토큰을 저장한다.
- 오래된 경로가 들어간 `rm` 스니펫을 현재 프로젝트에서 실행한다.
- `rsync --delete` 스니펫의 출발지와 목적지를 착각한다.
- 공개 동기화 저장소에 내부 서버명과 계정명이 올라간다.
- `pet search`에서 비슷한 설명의 스니펫을 잘못 선택한다.
- 설치 문서의 오래된 릴리즈 URL을 그대로 사용해 보안 패치가 빠진 버전을 설치한다.

## 10. 뇌 확장하기 (Evolution & Variants)

처음에는 개인 로컬 스니펫만 관리한다. 이후 다음 순서로 확장한다.

- 태그 규칙을 정한다.
- `danger`, `readonly`, `remote`, `docker`, `git` 같은 위험도와 영역 태그를 붙인다.
- 자주 쓰는 스니펫은 셸 키 바인딩과 연결한다.
- 팀 공유가 필요한 스니펫은 별도 저장소나 내부 문서로 옮긴다.
- 실행 명령과 설명 명령을 분리해 감사 가능성을 높인다.
- 오래된 스니펫을 정리하는 리뷰 주기를 둔다.

스니펫이 많아질수록 검색어 품질이 중요해진다. 명령 자체보다 "언제 쓰는지"를 설명에 적어야 나중에 찾기 쉽다.

## 11. 최종 체크리스트 (Definition of Done)

- [ ] 설치 전 공식 릴리즈와 패키지 버전을 확인했다.
- [ ] `fzf` 등 검색 의존성이 필요한지 확인했다.
- [ ] 민감 정보가 스니펫에 직접 들어가지 않았다.
- [ ] 파괴적 명령에는 `danger` 태그를 붙였다.
- [ ] 삭제와 동기화 명령에는 dry run 또는 대상 확인 스니펫을 함께 둔다.
- [ ] 동기화 저장소의 공개 범위를 확인했다.
- [ ] 오래된 스니펫을 정리할 기준을 정했다.
