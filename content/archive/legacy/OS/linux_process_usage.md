# 터미널 종료 뒤에도 Linux 프로세스 유지하기

이 문서는 Bash에서 시작한 장시간 작업이 터미널 또는 SSH 연결 종료의 영향을 받지 않도록 실행하는 방법을 설명합니다. 일회성 명령, 다시 접속할 대화형 작업, 재시작이 필요한 운영 작업을 구분해 선택해야 합니다.

## 먼저 구분할 개념

- **프로세스 ID(PID)**: 커널이 실행 중인 프로세스에 부여하는 번호입니다.
- **작업 ID(job ID)**: 현재 셸이 관리하는 작업 번호이며 `%1`, `%2`처럼 표시됩니다.
- **`disown`**: 현재 Bash의 작업 테이블만 다루는 셸 내장 명령입니다. 다른 셸이 시작한 PID를 현재 셸에서 `disown`할 수 없습니다.
- **SIGHUP**: 터미널 연결 종료 시 셸이나 터미널 계층에서 전달될 수 있는 신호입니다. SIGHUP만 무시한다고 해서 표준 입출력, 서비스 재시작, 사용자 세션 정책까지 해결되는 것은 아닙니다.

## 상황별 선택

| 상황 | 권장 수단 | 완료 상태 |
| --- | --- | --- |
| 로그만 남기는 일회성 명령 | `nohup`과 입출력 리디렉션 | 터미널 종료 뒤 PID가 살아 있고 로그가 기록됨 |
| 나중에 같은 화면으로 재접속할 작업 | `tmux` 또는 `screen` | 새 터미널에서 세션에 다시 접속 가능 |
| 장애 시 재시작해야 하는 운영 작업 | systemd 서비스 | 상태·로그·재시작 정책을 systemd에서 확인 가능 |
| 현재 셸에서 이미 시작한 작업 | `bg`와 `disown` | 현재 Bash의 `jobs` 목록에서 분리됨 |
| 다른 셸에서 시작한 작업 | 안전한 중단 후 관리 수단으로 재실행 | 새 실행의 PID와 로그 경로가 확인됨 |

## 새 작업을 시작할 때

### `nohup`: 비대화형 일회성 작업

표준 입력을 닫고 표준 출력과 오류를 명시적인 로그 파일로 보냅니다.

```bash
nohup your_command >your_command.log 2>&1 </dev/null &
pid=$!
printf 'pid=%s\n' "$pid"
```

현재 Bash의 작업 테이블에서도 제거하려면 같은 셸에서 다음 명령을 실행합니다.

```bash
disown %1
```

작업 번호는 고정값이 아니므로 실제 실행 전 `jobs -l`로 확인합니다. `nohup.out`에 암묵적으로 의존하지 않고 로그 경로를 지정하면 실행 결과와 디스크 사용량을 추적하기 쉽습니다.

### `tmux`: 상호작용과 재접속이 필요한 작업

```bash
tmux new -s backup
your_command
```

`Ctrl+B`를 누른 뒤 `D`를 눌러 세션을 분리합니다. 다시 접속할 때는 다음 명령을 사용합니다.

```bash
tmux attach -t backup
```

세션 목록에서 이름과 상태를 확인할 수 있어야 완료입니다.

```bash
tmux list-sessions
```

### `setsid`: 새 세션에서 실행

```bash
setsid your_command >your_command.log 2>&1 </dev/null &
```

`setsid`는 새 세션을 만들지만 로그 회전, 장애 재시작, 의존성 순서까지 관리하지 않습니다. 그런 요구가 있으면 systemd를 사용합니다.

## 현재 셸에서 이미 실행 중인 작업

포그라운드 작업을 중단 가능한 지점에서 `Ctrl+Z`로 일시 정지한 뒤, 같은 Bash에서 작업 번호를 확인하고 백그라운드로 전환합니다.

```bash
jobs -l
bg %1
disown -h %1
```

`disown -h`는 Bash가 종료될 때 해당 작업에 SIGHUP을 보내지 않도록 표시합니다. 작업을 Bash의 작업 목록에서도 제거하려면 `disown %1`을 사용합니다. 두 명령 모두 **현재 Bash가 관리하는 작업 ID**만 받습니다.

다음 명령은 올바른 대체 수단이 아닙니다.

```bash
disown 19446       # PID를 작업 ID처럼 사용할 수 없음
sudo disown %1     # disown은 외부 실행 파일이 아닌 현재 셸의 내장 명령
```

## 다른 셸에서 시작한 프로세스

다른 터미널에서 `kill -STOP`과 `kill -CONT`를 보내도 프로세스가 현재 셸의 작업 테이블로 이동하지 않습니다. 따라서 현재 셸에서 그 PID를 `disown`할 수 없습니다.

이 경우 다음 순서로 판단합니다.

1. 프로세스가 체크포인트, 재시작, 중복 실행 방지를 지원하는지 확인합니다.
2. 원래 명령, 인수, 작업 디렉터리, 환경 변수, 열린 파일을 기록합니다.
3. 데이터 손상 없이 중단할 수 있을 때만 정상 종료 신호를 보냅니다.
4. `nohup`, `tmux`, 또는 systemd 아래에서 새로 실행합니다.
5. 새 PID, 로그 경로, 처리 재개 지점을 확인한 뒤 이전 실행이 남아 있지 않은지 확인합니다.

프로세스를 무조건 종료하고 재실행하면 부분 기록, 중복 전송, 잠금 파일 같은 문제가 생길 수 있습니다. 작업의 재시작 계약을 모르면 종료하지 말고 해당 프로그램의 복구 절차를 먼저 확인합니다.

## 운영 작업은 systemd로 관리

백업이나 동기화처럼 반복 실행하거나 실패 후 재시작해야 하는 작업은 서비스 관리자가 적합합니다. 최소 단위 파일의 예시는 다음과 같습니다.

```ini
[Unit]
Description=Managed background job

[Service]
Type=simple
WorkingDirectory=/srv/job
ExecStart=/srv/job/run.sh
Restart=on-failure
StandardOutput=append:/var/log/managed-job.log
StandardError=inherit

[Install]
WantedBy=multi-user.target
```

경로, 실행 사용자, 권한, 재시작 정책은 실제 배포 환경에 맞게 정해야 합니다. 시스템 서비스라면 `systemctl status`, 사용자 서비스라면 `systemctl --user status`에서 활성 상태와 최근 오류를 확인합니다.

## 실행 상태 확인

확인 대상의 PID나 고유한 명령 패턴을 사용합니다. `ps aux | grep`만 사용하면 `grep` 자체나 이름이 비슷한 다른 프로세스가 섞일 수 있습니다.

```bash
ps -p "$pid" -o pid=,ppid=,stat=,lstart=,cmd=
pgrep -af '고유한-명령-패턴'
tail -n 50 your_command.log
```

다음 조건을 모두 확인해야 터미널 분리가 끝난 것입니다.

1. 원래 터미널을 종료한 뒤에도 대상 PID 또는 관리 서비스가 실행 중입니다.
2. 표준 입력이 닫혔거나 독립 세션에 연결되어 있습니다.
3. 표준 출력과 오류의 목적지가 확인됩니다.
4. 작업 자체의 진행 지표나 결과 파일이 계속 갱신됩니다.
5. 실패 시 재시작 주체와 중복 실행 방지 방식이 정해져 있습니다.

사용자 로그아웃 시 남은 프로세스를 종료하도록 구성된 시스템에서는 `nohup`만으로 충분하지 않을 수 있습니다. 이 정책까지 포함해 유지해야 한다면 systemd 시스템 서비스나 관리자가 승인한 사용자 서비스 설정을 사용합니다.
