# MCP와 REST API 배포 및 연결 안정성 비교

> **문서 상태:** 당시의 설계 비교를 정리한 보관 메모다. 도입 시점에 대상 클라이언트·SDK·프로토콜 버전·전송·인증·세션 지원을 확인한다. 기능 탐색은 호환성 차이를 드러내지만 파괴적 변경을 자동 해결하지 않는다.

외부 호스팅에서 엔드포인트 불일치 오류가 발생하는 주된 원인은 호출자(Client)와 제공자(Server)의 API 계약이 어긋나는 데 있다. REST API와 MCP(Model Context Protocol)는 이 계약을 다루는 방식이 다르다.

## 1. 배포 및 연결 아키텍처

### REST API + OpenAPI

REST API의 URL·버전·스키마를 클라이언트와 합의한다. 주소는 하드코딩 외에 설정·서비스 탐색으로 관리할 수도 있다.

- 서버를 공인 IP 또는 도메인(`api.myserver.com`)으로 노출한다.
- 외부망 클라이언트가 접근하려면 방화벽 개방, SSL 인증서, Nginx 리버스 프록시, Cloudflare Tunnel(`cloudflared`) 같은 네트워크 구성이 필요하다.
- 클라이언트 코드에는 URL(`https://.../chat`)을 하드코딩하거나 환경변수로 주입한다.
- 클라이언트 개발자는 API 명세(`openapi.yaml`)를 기준으로 요청 필드와 응답 구조를 직접 맞춘다.

### MCP

MCP는 동적 탐색과 협상에 가까운 방식이다.

- **Local(Stdio)**: Cursor나 Claude Desktop이 SSH, Docker 명령어 등으로 서버 프로세스를 직접 실행하고 표준 입출력(stdin/stdout)으로 통신한다. 외부 포트, 도메인, 방화벽 개방이 필요하지 않다.
- **Remote**: 선택한 프로토콜·SDK가 지원하는 HTTP 전송을 구성한다. 예를 들어 [2025-11-25 전송 명세](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)는 Streamable HTTP를 정의하고 구형 HTTP+SSE와의 호환 경로를 구분한다. SSE라는 이름만으로 서버·클라이언트 호환성을 판단하지 않는다.
- 지원 버전의 연결 초기화·기능 협상 절차를 따른 뒤 도구 목록·스키마를 탐색한다. 초기 handshake가 도구 목록 전체나 업무 준비 상태를 자동으로 증명하는 것은 아니다.
- 클라이언트는 서버의 tool 목록과 JSON Schema를 받아 기능을 동적으로 구성한다.

## 2. 엔드포인트 불일치 비교

| 상황 | REST API | MCP |
| :--- | :--- | :--- |
| 엔드포인트 변경 | URL·경로가 바뀌면 구성·소비자 갱신 전까지 연결 실패나 404가 발생할 수 있음 | 전송 URL 변경은 구성 갱신이 필요하고 도구 탐색은 연결 이후 제공 기능의 차이를 찾는 데 도움을 줌 |
| 파라미터 변경 | 필수 필드 추가는 명세·생성 클라이언트·호환 버전 검토가 필요 | 새 JSON Schema를 탐색해도 기존 프롬프트·클라이언트·모델이 필드를 올바르게 채운다는 보장은 없음 |
| 서버 상태 확인 | `/health` 등 생존·준비 상태 계약을 설계하고 검사 | 프로토콜 연결 확인만으로 DB·외부 서비스·각 도구의 준비 상태를 증명하지 못하며 별도 검사 필요 |

## 3. 배포 시나리오

### 로컬 Docker 컨테이너를 여러 프로젝트에서 사용

REST API는 컨테이너 포트(`7016`)가 `localhost`에서 충돌 없이 떠 있어야 하며, 각 프로젝트의 `.env`에 `http://localhost:7016` 값을 둔다. 포트 관리가 필요하다.

MCP Stdio는 지원 클라이언트에 `docker run -i ...` 같은 실행 명령을 구성할 수 있다. 로컬 stdio 자체에는 외부 포트가 필요 없지만 이미지 버전·실행 권한·비밀 주입·프로세스 종료·프로젝트별 상태 격리를 함께 관리한다.

### 원격 서버의 에이전트 사용

REST API는 SSL 인증서, 도메인 연결, 인증 로직이 필요하다. 현재 프로젝트가 Cloudflare Access에 의존하는 구조라면 API Key 등 별도 인증 설계를 추가로 검토한다.

MCP 원격 연결도 TLS·인증·네트워크·세션 정책이 필요하다. 연동 비용은 대상 클라이언트의 지원 범위와 필요한 어댑터에 따라 달라지며 프로토콜 이름만으로 더 낮다고 판정하지 않는다.

## 4. 구성안

NoAICode가 이미 REST API를 제공한다면 기존 REST API를 유지하고 MCP 어댑터를 추가하는 구성이 가능하다.

1. 웹 및 모바일 앱 연동: 기존 REST API 사용
2. IDE(Cursor)와 개인 워크플로우 연동: MCP(Stdio/Docker) 사용

이 구성은 서비스 트래픽 처리에는 REST API를 사용하고, 로컬 개발 도구 연동에는 MCP의 동적 tool 탐색을 사용하는 방식이다.

## 도입 완료 기준

대상 클라이언트 목록, 지원 버전·전송, 인증, 도구 삭제·이름 변경·필수 필드 추가의 호환성 시험, 연결 중단 후 복구를 기록한다. 이 근거가 없으면 REST와 MCP를 함께 두는 구성은 설계 후보로 남는다.
