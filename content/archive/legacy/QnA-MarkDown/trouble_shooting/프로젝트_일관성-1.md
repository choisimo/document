# 프로젝트 간 API 불일치 방어 전략

> **증거 경계:** 이 문서는 API 계약을 관리하는 설계안이다. `openapi.yaml`, `validateDto`, `src/middlewares/index.js`와 `npm test`는 대상 프로젝트에서 실제 경로·등록·검증 범위를 확인한 경우에만 현재 구현의 근거로 삼는다. 서버 구현·명세·생성 클라이언트·소비자 기대 중 둘 이상이 어긋나면 API Drift가 발생한다.

리팩토링 과정에서 발생하는 프로젝트 간 불일치(API Drift)는 백엔드 개발자가 API 명세나 로직을 변경했을 때 이를 사용하는 클라이언트가 변경 사실을 반영하지 못해 생긴다. `openapi.yaml`이 있는 프로젝트에서는 OpenAPI 명세를 단일 기준으로 삼아 불일치를 감지할 수 있다.

## 1단계: 설계 단계 방어

### OpenAPI Diff 도구

백엔드 리팩토링에서 필드명 변경(`sessionId` -> `session_id`)이나 required 값 추가처럼 하위 호환성을 깨뜨리는 변경은 CI/CD 단계에서 감지한다.

- 사용 도구 예시: Optic, openapi-diff
- 작동 방식: PR 시점에 기준 브랜치와 변경 브랜치의 OpenAPI 명세를 비교한다. 명세 diff만으로 실제 코드 동작을 검사할 수 없으므로 구현·응답 검증은 별도로 실행한다.
- 파괴적 변경을 필수 CI 실패로 연결한다. 선택한 도구 버전의 종료 코드·실패 옵션을 확인하고 실제 파괴적 변경 예제로 배포 차단을 검증한다.

```bash
# 예시: openapi-diff 실행
docker run --rm -v "$PWD:/specs:ro" "${OPENAPI_DIFF_IMAGE:?set a tested image tag or digest}" /specs/openapi_old.yaml /specs/openapi_new.yaml
```

### 타입 자동 생성

검증한 OpenAPI 경로를 기준으로 클라이언트 타입을 생성한다. 생성 도구는 테스트한 버전으로 개발 의존성과 lockfile에 고정하고 CI에서 동일하게 설치한다.

- 사용 도구 예시: openapi-typescript
- 효과: DTO와 명세를 함께 갱신한 뒤 타입 재생성·생성물 변경 확인·모든 소비자 빌드를 CI에서 강제해야 없는 속성 참조를 찾을 수 있다. 타입 생성만으로 의미·인증·실행 결과가 검증되지는 않는다.

```bash
# 백엔드 스펙 기반으로 클라이언트 타입 생성
npx --no-install openapi-typescript ./src/openapi.yaml -o ./client/src/types/api.d.ts
```

## 2단계: 테스트 단계 방어

Contract Testing은 API가 약속한 요청과 응답을 지키는지 검증한다.

- 사용 도구 예시: Pact
- Consumer(클라이언트)는 예상 요청과 응답을 계약 파일로 정의한다.
- Provider(백엔드)는 CI 파이프라인에서 이 계약 파일을 기준으로 테스트를 실행한다.
- 리팩토링 후 응답 형식이 달라지면 테스트가 실패한다.

NoAICode 같은 대상 프로젝트에 적용할 흐름의 예시는 다음과 같다. 실제 테스트 등록과 provider 실행 경로는 별도로 확인한다.

1. 클라이언트(Cursor, Web UI 등) 측에서 Pact 계약을 정의한다.
2. 백엔드 테스트(`npm test`)에서 Pact 요청을 실제 서버에 보낸다.
3. 응답 형식이 계약과 다르면 테스트를 실패 처리한다.

## 3단계: 런타임 방어

Schema Validation Middleware는 요청과 응답이 OpenAPI 명세와 일치하는지 런타임에 검사한다.

- 확인할 상태: `validateDto`가 존재한다면 실제 등록 경로와 요청 검증 범위를 코드로 확인한다. 이 문서만으로 대상 프로젝트의 현재 상태를 단정하지 않는다.
- 개선안: `express-openapi-validator` 같은 라이브러리를 추가하여 응답까지 검증한다.
- 효과: 리팩토링 중 `timestamp` 필드 누락 같은 문제가 발생하면 서버 로그에 응답 검증 오류가 남는다.

## 적용 순서

1. Level 1: `openapi-typescript`로 백엔드 API 명세 기반 클라이언트 타입을 자동 생성한다.
2. Level 2: `express-openapi-validator`를 `src/middlewares/index.js`에 추가해 명세와 다른 응답을 감지한다.
3. Level 3: 팀 단위 개발에서는 Pact로 클라이언트-서버 계약 테스트를 자동화한다.

`openapi.yaml`이 이미 관리되는 프로젝트에서는 타입 자동 생성만 적용해도 리팩토링으로 인한 다수의 불일치 사고를 줄일 수 있다.

## 완료 판정

명세 diff·타입 재생성과 소비자 빌드·실제 요청 및 응답 계약 검사를 서로 독립된 필수 증거로 둔다. 응답 검증 실패를 운영에서 어떻게 처리할지와 성능 영향, 소비자별 계약 소유자·호환 버전 정책도 정한다. 세 단계는 서로 대체하지 않으며 선택한 릴리스의 실제 출력이 모두 일치할 때만 계약 일치로 기록한다.
