리팩토링 과정의 **"프로젝트 간 불일치(API Drift)"**는 서버 구현, API 명세, 생성 클라이언트, 소비자 기대 중 둘 이상이 서로 다른 계약을 가리킬 때 발생합니다.

이 문서에는 OpenAPI Specification 경로로 **`<span class="citation-72">src/openapi.yaml</span>`**이 인용되어 있습니다.^1^ 현재 저장소에서 해당 파일과 생성 경로를 확인한 경우에만 이를 계약 기준으로 채택합니다. 명세를 기준으로 삼더라도 구현 검증과 소비자 테스트가 없으면 단일 진실의 원천이 되지 않습니다.

---

### 1단계: 설계 단계 방어 - "문서와 코드의 동기화 강제" (가장 추천)

가장 비용이 적게 들고 효과적인 방법은 **"코드가 바뀌면 문서가 깨지거나, 문서가 바뀌면 경고를 띄우는 것"**입니다.

#### A. OpenAPI Diff 도구 도입 (Breaking Change 감지)

백엔드 리팩토링 시 실수로 필드명을 바꾸거나(`sessionId` -> `session_id`), 필수 값을 추가하여 하위 호환성을 깨뜨리는 것을 CI/CD 단계에서 잡아냅니다.

* **추천 도구:** **Optic** 또는 **openapi-diff**
* **작동 방식:** PR(Pull Request)이 올라올 때 기준 브랜치의 `openapi.yaml`과 변경 브랜치의 `openapi.yaml`을 비교합니다. 이 비교는 명세 간 차이를 찾으며, 수정된 코드의 실제 동작은 별도의 구현·응답 검증으로 확인해야 합니다.
* 적용 방법:
  Github Actions 워크플로우(docker-publish.yml 등)에 체크 단계를 추가합니다.
  **Bash**

  ```
  # 예시: openapi-diff 실행
  docker run --rm -v $(pwd):/specs openapitools/openapi-diff:latest /specs/openapi_old.yaml /specs/openapi_new.yaml
  ```

  만약 "Breaking Change(파괴적 변경)"가 감지되면 배포를 막습니다.

#### B. 타입 자동 생성 (Codegen)

백엔드의 `openapi.yaml`을 기준으로 프론트엔드/클라이언트가 사용할 **TypeScript 타입 정의 파일(.d.ts)**을 자동으로 생성해버리는 방식입니다.

* **추천 도구:** **openapi-typescript**
* **효과:** 백엔드에서 `<span class="citation-71">ChatResponseDto</span>`^2^의 필드명을 바꾸고 `openapi.yaml`을 업데이트한 뒤 타입 재생성과 클라이언트 빌드를 CI에서 강제하면, 존재하지 않는 속성 참조를 컴파일 단계에서 찾을 수 있습니다.
  **Bash**

  ```
  # 백엔드 스펙 기반으로 클라이언트 타입 생성
  npx openapi-typescript ./src/openapi.yaml -o ./client/src/types/api.d.ts
  ```

### 2단계: 테스트 단계 방어 - "Contract Testing (계약 테스트)"

API가 "약속(계약)한 대로 응답을 주는지" 검증하는 가장 확실한 방법입니다.

* **추천 도구:** **Pact** (가장 유명한 표준)
* **개념:** Consumer(클라이언트)가 "나는 이런 요청을 보낼 거고, 이런 응답을 기대해"라는 계약서(Pact file)를 작성합니다. Provider(백엔드)는 CI 파이프라인에서 이 계약서를 바탕으로 테스트를 돌립니다.
* **NoAICode 적용:**
  1. 클라이언트(예: Cursor, Web UI) 측에서 Pact를 정의합니다.
  2. 리팩토링 후 백엔드 테스트(`npm test`)가 돌 때 Pact가 정의된 요청을 백엔드에 실제로 날려봅니다.
  3. 응답 형식이 조금이라도 다르면 테스트가 실패합니다.

### 3단계: 런타임 방어 - "Schema Validation Middleware"

**현재 프로젝트에는 **`<span class="citation-70">validateDto</span>` 미들웨어 ^3^가 존재합니다. 이를 더 강화하여, **요청뿐만 아니라 응답(Response)까지 검증**하도록 설정하면 리팩토링 실수를 실시간으로 잡을 수 있습니다.

* **현재 상태:** 요청(`<span class="citation-69">req.body</span>`)은 DTO로 검증 중^4^.
* **개선 방안:** `express-openapi-validator` 같은 라이브러리를 미들웨어로 장착합니다.
  * **이 미들웨어는 **`<span class="citation-68">openapi.yaml</span>`^5^을 로드하여, 서버가 내보내는 응답 데이터가 명세서와 100% 일치하는지 감시합니다.
  * 리팩토링 중 실수로 `timestamp` 필드를 누락했다면, 서버 로그에 "Response validation failed" 에러가 찍히게 됩니다.

### 💡 요약 및 추천 로드맵

리팩토링에 따른 불일치를 막기 위해 **비용 대비 효과가 가장 큰 순서**대로 적용하세요.

1. **즉시 적용 (Level 1):** `openapi-typescript`를 설치하여, 백엔드 API 명세가 바뀔 때마다 프론트엔드/SDK의 타입이 깨지도록 만드십시오. (가장 쉽고 강력함)
2. **안정화 (Level 2):**`<span class="citation-67">express-openapi-validator</span>`를 `<span class="citation-67">src/middlewares/index.js</span>`^6^에 추가하여, 문서와 다른 응답을 보내면 서버가 에러를 뱉도록 강제하십시오.
3. **고도화 (Level 3):** 팀 단위 프로젝트라면 **Pact**를 도입하여 클라이언트-서버 간의 계약을 자동화하십시오.

Level 1 완료 조건은 명세 변경 감지, 타입 재생성, 생성물 변경 여부 확인, 모든 소비자 빌드를 하나의 필수 CI 작업으로 묶는 것입니다. Level 2는 요청·응답 검증 실패의 운영 정책과 성능 영향을 승인해야 완료됩니다. Level 3는 소비자별 계약 소유자와 호환 버전 정책이 있어야 합니다.

이 세 단계는 서로 대체하지 않습니다. 명세 diff는 변경을 분류하고, codegen은 정적 사용처를 검사하며, 계약·런타임 테스트는 실제 요청과 응답을 확인합니다. 세 근거가 모두 통과한 릴리스만 `계약 일치` 상태로 표시합니다.
