# 프로젝트 간 API 불일치 방어 전략

리팩토링 과정에서 발생하는 프로젝트 간 불일치(API Drift)는 백엔드 개발자가 API 명세나 로직을 변경했을 때 이를 사용하는 클라이언트가 변경 사실을 반영하지 못해 생긴다. `openapi.yaml`이 있는 프로젝트에서는 OpenAPI 명세를 단일 기준으로 삼아 불일치를 감지할 수 있다.

## 1단계: 설계 단계 방어

### OpenAPI Diff 도구

백엔드 리팩토링에서 필드명 변경(`sessionId` -> `session_id`)이나 required 값 추가처럼 하위 호환성을 깨뜨리는 변경은 CI/CD 단계에서 감지한다.

- 사용 도구 예시: Optic, openapi-diff
- 작동 방식: PR 시점에 기존 `openapi.yaml`과 수정된 명세 또는 실제 동작을 비교한다.
- 파괴적 변경이 감지되면 배포를 중단한다.

```bash
# 예시: openapi-diff 실행
docker run --rm -v $(pwd):/specs openapitools/openapi-diff:latest /specs/openapi_old.yaml /specs/openapi_new.yaml
```

### 타입 자동 생성

백엔드의 `openapi.yaml`을 기준으로 프론트엔드나 SDK에서 사용할 TypeScript 타입 정의 파일을 자동 생성한다.

- 사용 도구 예시: openapi-typescript
- 효과: 백엔드 DTO 필드 변경 후 명세가 갱신되면 클라이언트 빌드 단계에서 없는 속성 참조가 컴파일 오류로 드러난다.

```bash
# 백엔드 스펙 기반으로 클라이언트 타입 생성
npx openapi-typescript ./src/openapi.yaml -o ./client/src/types/api.d.ts
```

## 2단계: 테스트 단계 방어

Contract Testing은 API가 약속한 요청과 응답을 지키는지 검증한다.

- 사용 도구 예시: Pact
- Consumer(클라이언트)는 예상 요청과 응답을 계약 파일로 정의한다.
- Provider(백엔드)는 CI 파이프라인에서 이 계약 파일을 기준으로 테스트를 실행한다.
- 리팩토링 후 응답 형식이 달라지면 테스트가 실패한다.

NoAICode 적용 흐름은 다음과 같다.

1. 클라이언트(Cursor, Web UI 등) 측에서 Pact 계약을 정의한다.
2. 백엔드 테스트(`npm test`)에서 Pact 요청을 실제 서버에 보낸다.
3. 응답 형식이 계약과 다르면 테스트를 실패 처리한다.

## 3단계: 런타임 방어

Schema Validation Middleware는 요청과 응답이 OpenAPI 명세와 일치하는지 런타임에 검사한다.

- 현재 상태: `validateDto` 미들웨어가 요청(`req.body`)을 DTO로 검증한다.
- 개선안: `express-openapi-validator` 같은 라이브러리를 추가하여 응답까지 검증한다.
- 효과: 리팩토링 중 `timestamp` 필드 누락 같은 문제가 발생하면 서버 로그에 응답 검증 오류가 남는다.

## 적용 순서

1. Level 1: `openapi-typescript`로 백엔드 API 명세 기반 클라이언트 타입을 자동 생성한다.
2. Level 2: `express-openapi-validator`를 `src/middlewares/index.js`에 추가해 명세와 다른 응답을 감지한다.
3. Level 3: 팀 단위 개발에서는 Pact로 클라이언트-서버 계약 테스트를 자동화한다.

`openapi.yaml`이 이미 관리되는 프로젝트에서는 타입 자동 생성만 적용해도 리팩토링으로 인한 다수의 불일치 사고를 줄일 수 있다.
