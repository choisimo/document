# SSHFS 권한 문제: 동일 유저명에도 불구하고 발생하는 접근 제한 원인

SSHFS로 원격 사용자의 `0700` 디렉터리에 접근하지 못한 사례를 진단합니다. 같은 사용자 이름은 로컬 UID와 원격 UID가 같다는 증거가 아니며, 오류가 원격 SSH 권한·FUSE 로컬 권한·마운트 지점 권한 중 어디서 발생했는지 먼저 구분합니다.

## 주요 원인

### 1. UID/GID 불일치 문제

가능한 원인 하나는 로컬과 원격 시스템의 UID/GID 또는 SSHFS 매핑 방식이 다르다는 것입니다. 빈도는 이 문서의 근거만으로 판정하지 않습니다.

```bash
# 로컬과 원격 시스템에서 각각 실행하여 ID 확인
id nodove
```

예를 들어 로컬에서 nodove의 UID가 1000이고, 원격에서는 1001이면 권한 문제가 발생합니다[1].

### 2. SSHFS 마운트 옵션 문제

`default_permissions` 옵션을 사용할 경우, 권한 제어가 FUSE가 아닌 커널에 의해 처리됩니다. 이 경우 원격 사용자의 UID/GID가 로컬 사용자와 매핑되지 않습니다[1].

권한 문제는 다음 마운트 옵션을 사용하여 해결할 수 있습니다:
```bash
sshfs -o idmap=user nodove@원격서버:/경로 /마운트지점
```

### 3. sudo 사용 관련 문제

SSHFS는 사용자 공간 프로세스이므로 `sudo`로 실행할 필요가 없습니다. `sudo`로 실행하면 SSH 키 인증 시 `/home/nodove/.ssh`가 아닌 `/root/.ssh`에서 키를 찾게 됩니다[3].

또한 `sudo`로 마운트된 디렉토리에 접근하려면 `allow_other` 옵션이 필요합니다:
```bash
sudo sshfs -o allow_other nodove@원격서버:/경로 /마운트지점
```

### 4. 부모 디렉토리 권한 문제

마운트하려는 디렉토리의 상위 디렉토리들도 적절한 접근 권한이 있어야 합니다. 경로 중간에 권한이 700인 디렉토리가 있으면, 그 안의 디렉토리에 권한이 777이더라도 접근할 수 없습니다[2].

## 해결 방법

1. **UID/GID 확인 및 맞추기**:
   ```bash
   # 로컬 시스템의 UID/GID 확인
   id nodove
   
   # 원격 시스템의 UID/GID 확인
   ssh nodove@원격서버 "id"
   ```
   
   UID 변경은 원격 파일 전체의 소유권과 다른 서비스에 영향을 줄 수 있으므로 즉시 수행하지 않습니다. 먼저 `idmap`, 명시적 `uid/gid`, 원격 소유권 중 어떤 모델을 사용할지 정하고 테스트 마운트에서 확인합니다.

2. **적절한 마운트 옵션 사용**:
   ```bash
   sshfs nodove@원격서버:/경로 /마운트지점 -o idmap=user,uid=$(id -u),gid=$(id -g)
   ```

3. **fuse.conf 설정 확인**:
   ```bash
   # /etc/fuse.conf 파일에서 user_allow_other 옵션이 활성화되어 있는지 확인
   sudo nano /etc/fuse.conf
   # 다른 로컬 사용자에게 접근을 허용해야 할 때만 user_allow_other 검토
   ```

`allow_other`는 해결을 위한 기본 옵션이 아니라 접근 범위를 넓히는 정책입니다. 완료 조건은 의도한 로컬 사용자만 파일을 읽고 쓸 수 있고, 비허용 사용자는 거부되며, 재마운트 뒤에도 같은 UID/GID와 권한 결과가 유지되는 것입니다.
